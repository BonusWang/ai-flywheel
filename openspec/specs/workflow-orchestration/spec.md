# workflow-orchestration Specification

## Purpose
一次 P00–P07 沉淀运行的完整生命周期：独占锁、固定 8 节点状态机、准备与准入、只读的全文审查与错题候选、路由与写入计划、审批门、受控写入、结算、报告与交付，以及失败时的 fail-run 契约。
## Requirements
### Requirement: 独占运行锁
系统 SHALL 保证同一时刻只有一个运行持有独占锁。已有运行持锁时再次启动 MUST 抛出 `WorkflowLockError`，且不创建新运行。安全阀 `WORKFLOW_ENABLED` 关闭时 MUST 拒绝启动。

#### Scenario: 重复启动被拒绝
- **WHEN** 已有运行持有独占锁时再次启动运行
- **THEN** 抛出 `WorkflowLockError` 并指明当前持锁运行，不产生新的运行记录

### Requirement: 固定 8 节点状态机与节点回执
每次运行 SHALL 依次经过 P00 准备、P01 启动、P02 审查、P03 路由与计划、P04 写入与验收、P05 结算、P06 报告、P07 交付八个节点。每个节点结束时 MUST 把节点快照写入不可变回执存储并记录回执哈希前缀，同时向事件总线发布节点状态更新。

#### Scenario: 节点结束落回执
- **WHEN** 任一节点进入终态
- **THEN** 在回执存储生成 `runs/{run_id}/{node_id}` 回执，运行记录带该回执的哈希前缀

### Requirement: P00 准备与对账
P00 SHALL 校验内置策略完整性、按配置的扫描源对账登记新会话，并在未显式指定会话时执行规则初筛；初筛跳过数大于 0 时 MUST 追加 `triage_skipped` 审计事件。待审会话取显式指定的会话，否则取 `pending` 会话并按 P0 核心、P1 信号、P1 一般、P2 元信息的优先级排序。

优先级排序 MUST 落在 SQL 里，不得对一页有限的结果在内存里排序——否则落在窗口之外的高优先级会话会被饿死。显式指定的会话 MUST 逐个按会话键取回，不得靠过滤一页最近会话。

#### Scenario: 初筛跳过留痕
- **WHEN** 规则初筛跳过了临时或碎片会话
- **THEN** P00 摘要给出跳过数量，并写入 `triage_skipped` 审计事件

#### Scenario: 高优先级会话不被饿死
- **WHEN** 待审会话里有一条 P0 核心会话排在结果窗口之外
- **THEN** 该会话仍出现在按优先级排序的待审列表首位

#### Scenario: 显式指定的会话逐个取回
- **WHEN** 调用方显式指定了一个不在最近会话窗口里的会话
- **THEN** 该会话仍被准入本轮

### Requirement: P01 独占准入
P01 SHALL 在单次运行会话数上限与总字符预算内依次准入候选会话（单会话正文截取上限 24000 字符），把准入会话置为 `in_progress`。继续准入将超预算且已有准入会话时 MUST 停止准入。

使用模型执行器（`api` / `cli`）时，单次准入的会话数 MUST 不超过模型审查一次能读完的会话数上限，多出来的会话 MUST 留在 `pending` 等待下一批，不得被准入后跳过审查又按已沉淀结算。

#### Scenario: 字符预算截断准入
- **WHEN** 下一个候选会话会使总字符数超过 `max_chars_per_run`，且已有至少一个准入会话
- **THEN** 停止准入，P01 摘要给出准入数量与已用字符数

#### Scenario: 多出来的会话留在队列里
- **WHEN** 待审会话数超过模型审查一次能读完的会话数上限
- **THEN** 本轮只准入上限内的会话，其余仍是 `pending`

### Requirement: P02 全文审查与错题候选
P02 SHALL 调用执行器审查准入会话。执行器按配置选择：`api` 模式且已配置地址与模型时用 OpenAI 兼容 API，`cli` 模式且已配置命令时用本地 CLI，否则用零成本的启发式演练执行器。

P02 SHALL 只读：审查产出的错题与分歧 MUST 只作为候选保留在节点载荷里，不得写入错题观察池或分歧表。可晋升清单 MUST 由两处合成：观察池里仍在观察中且为高危沉默错误或自查拦截类累计出现不少于 3 次的记录，以及本次审查发现、其预计出现次数（已有次数加上本次新增，出现过同一会话的会话不重复计数）达到门槛的错题。分歧与反例 MUST 单独留存，不覆盖既有规则。

候选列表 MUST 写进节点载荷，使审批挂起或进程重启后候选仍然可用。错题候选与分歧候选的落库 MUST 推迟到 P04，即审批放行之后。

P02 MUST 在节点摘要与节点载荷里写明审查来源（模型、本地 CLI 或本地启发式审查器），并写明本次实际送审的会话键。执行器的审查结果没有声明来源时，节点 MUST 写明来源未声明，不得推断。

执行器报告审查不可用时，P02 MUST 按 fail-run 契约失败：节点为 `FAILED`，节点摘要与载荷保留原因与诊断，追加 `review_unavailable` 审计事件；不得改用其他审查器，不得把任何错题或分歧写入观察池。

#### Scenario: 自查拦截类满三次进入可晋升
- **WHEN** 同一根因键的自查拦截类错题累计出现 3 次
- **THEN** 该错题进入本轮可晋升清单

#### Scenario: 高危沉默错误首次即可晋升
- **WHEN** 审查产出一条高危沉默错误
- **THEN** 该错题首次出现即进入本轮可晋升清单

#### Scenario: P02 不写观察池
- **WHEN** P02 审查出了错题与分歧
- **THEN** 错题观察池与分歧表没有新增记录，候选只出现在 P02 节点载荷里

#### Scenario: 模型审查不可用时整轮失败
- **WHEN** `api` 模式下模型的 P02 回复在格式修复后仍不是 JSON 对象
- **THEN** P02 为 `FAILED`，P03–P07 为 `SKIPPED`，运行为 `FAILED`，准入会话回到 `pending`，独占锁已释放；节点摘要与载荷写明原因；存在 `review_unavailable` 与 `run_failed` 审计事件；错题观察池没有新增记录，知识库与技能目录没有任何新增文件

#### Scenario: 模型没有给出任何发现
- **WHEN** `api` 模式下提示词里有会话，模型返回空的 `findings`
- **THEN** P02 为 `FAILED`，诊断的原因是没有发现；磁盘上已存在同一批次的坏缓存文件时，失败信息给出该缓存文件名

#### Scenario: 审查来源写进节点
- **WHEN** `runner.mode` 为 `api` 且模型返回可用的审查
- **THEN** P02 为 `PASS`，节点摘要写明审查来源为 API 模型，节点载荷的 `review_source` 为 `model`

#### Scenario: 演练模式标明审查来源
- **WHEN** `runner.mode` 为 `dry_run`
- **THEN** P02 摘要写明审查来自本地启发式审查器，节点载荷的 `review_source` 为 `heuristic`

#### Scenario: 执行器没有声明来源
- **WHEN** 执行器的审查结果里没有来源
- **THEN** P02 照常通过，节点摘要写明审查来源未声明

### Requirement: P03 路由与写入计划
P03 SHALL 调用执行器生成写入计划：与既有规则和技能查重，写入项数量不超过 `max_writes_per_run` 与知识落点 `max_write_set` 的较小值；计划文档的默认前缀取第一个允许写入前缀。单批上限 MUST 按"保留下来的写入数"计，不得按读到的项序号计——不合规的项 MUST NOT 占用后面合规项的名额。

计划项进入写入环节前 MUST 过隐私前置门：正文里的 `<private>...</private>` 片段先脱敏，正文或规则标题、检查项里出现凭据的整项丢弃并留痕。写入环节的隐私与密钥门禁 MUST 保留，作为第二道防线。

P03 MUST 在节点摘要与节点载荷里写明计划来源（模型、本地 CLI 或本地启发式计划器）。

执行器报告有计划项被丢弃或未列入时，P03 MUST 在节点摘要里给出数量，在节点载荷里列出明细，并追加 `plan_items_dropped` 审计事件；节点不得因此失败。

执行器报告计划不可用时，P03 MUST 按 fail-run 契约失败：节点为 `FAILED`，节点载荷保留逐项原因，有被丢弃项时先追加 `plan_items_dropped` 审计事件；不得改用其他计划器，不得产生任何写入。

执行器报告有重复流程候选未生成 Skill 计划时，P03 MUST 在节点摘要里给出数量，在节点载荷里列出候选，并追加 `skill_candidates_deferred` 审计事件。

挂载 Schema 治理的 Wiki 时，P03 还 MUST：

- 发现路由候选集，并随计划请求交给执行器；
- 执行器为模型执行器（`api` / `cli`）时，提示词 MUST 包含候选集，并要求每项 `knowledge_doc` 声明页面类型、项目（或显式"无归属"）与理由；执行器 MUST 把声明原样带到计划项上，校验前不改写；
- 对每项 `knowledge_doc` 先做路由声明校验，结论为写入的再执行 T5 归一化；
- 留痕：已路由与未路由两张清单进节点载荷，分别写 `planned_doc_routed` 与 `planned_doc_unrouted` 审计事件，节点摘要给出未写入的数量与原因分布。

#### Scenario: 写入项数量受限
- **WHEN** 执行器返回的写入项超过单批上限
- **THEN** 只保留上限内的写入项，P03 内部检查记录计划数与上限

#### Scenario: 不合规项不占用名额
- **WHEN** 执行器返回的项里有不合规项排在合规项前面，且总数超过单批上限
- **THEN** 保留的写入项数等于单批上限，不合规项被丢弃并留痕

#### Scenario: 部分丢弃留痕
- **WHEN** `api` 模式下模型返回 5 项，其中 1 项不合规
- **THEN** 运行继续，P03 为 `PASS`；节点摘要写明计划来源为模型、1 项未列入；节点载荷列出该项的序号、类型与原因；存在 `plan_items_dropped` 审计事件

#### Scenario: 全部无效时整轮失败
- **WHEN** `api` 模式下模型的计划项全部不合规
- **THEN** P03 为 `FAILED`，P04–P07 为 `SKIPPED`，运行为 `FAILED`，准入会话回到 `pending`，独占锁已释放；存在 `plan_items_dropped` 与 `run_failed` 审计事件；写入计划为空，知识库与技能目录没有任何新增文件

#### Scenario: 带凭据的计划项被丢弃
- **WHEN** 模型的知识文档项正文里含未脱敏的凭据
- **THEN** 该项在进入写入计划前被丢弃并留痕，本轮不写入任何内容

#### Scenario: 演练模式标明来源与未成计划的 Skill 候选
- **WHEN** `runner.mode` 为 `dry_run`，审查结果含重复流程候选
- **THEN** P03 摘要写明计划来自本地启发式计划器并给出未生成计划的候选数量，写入计划里没有 Skill 项，存在 `skill_candidates_deferred` 审计事件

#### Scenario: 候选集进入提示词
- **WHEN** 门禁适用且执行器为模型执行器
- **THEN** P03 提示词包含可路由页面类型，以及每个候选项目的目录名、`project_id`、别名与描述

#### Scenario: 按声明归属的笔记被写入并留痕
- **WHEN** 模型为某篇知识文档声明的项目与证据不冲突
- **THEN** 该笔记归一化到声明项目的 `实战笔记/` 下，存在 `planned_doc_routed` 审计事件，节点载荷中它的路由来源为 `declared`

#### Scenario: 草稿无项目标识但声明正确
- **WHEN** 草稿全文没有声明项目的标识，工作区也没有命中
- **THEN** 该笔记仍按声明写入

#### Scenario: 演练执行器的计划走证据判定
- **WHEN** 门禁适用且执行器为零配置演练执行器
- **THEN** 知识文档按证据判定归属，节点载荷中它的路由来源为 `evidence`

### Requirement: 审批门
P03 之后系统 SHALL 按生效审批模式决定是否挂起：`auto` 不挂起；`always` 只要有写入计划就挂起；`smart` 仅在出现 Skill 封装 / 优化、标记需审批、删除或覆盖核心文件，或写入项数超过高写入阈值时挂起。调用方显式传入的自动放行 / 强制审批覆盖优先于配置。

挂起时 P04 置为等待审批、运行置为 `AWAITING_APPROVAL`，系统 MUST 追加 `awaiting_approval` 审计事件，创建决策卡并登记门户投递；飞书通道启用时一并登记飞书投递。决策卡的选项为「同意并写入」「取消本次写入」，计划同时含常规项与敏感情项时增加「仅同意常规项」。敏感情项指 Skill 封装 / 优化、标记需审批、删除或覆盖核心文件的写入项，其余为常规项。通道的发送与状态回写按 `approval-card-channels` 执行。

#### Scenario: smart 模式遇 Skill 变更挂起
- **WHEN** 审批模式为 `smart`，且计划含 Skill 封装或优化项
- **THEN** 运行在 P03 后挂起等待审批，P04 置为等待审批

#### Scenario: smart 模式常规笔记直接放行
- **WHEN** 审批模式为 `smart`，计划只含常规笔记与规则且数量不超过高写入阈值
- **THEN** 运行不挂起，追加 `auto_approved` 审计事件后直接进入 P04

#### Scenario: 人工批准后续跑
- **WHEN** 对等待审批的运行批准了部分写入项
- **THEN** 仅被批准的项进入 P04，运行状态回到运行中并继续执行

#### Scenario: 混合批次提供仅同意常规项
- **WHEN** 挂起的运行同时含常规项与敏感情项，维护者选择「仅同意常规项」
- **THEN** 只有常规项进入 P04，敏感情项不写入，决策卡记录所选的选项

### Requirement: 拒绝放行
对等待审批的运行执行拒绝时，系统 SHALL 把准入会话恢复为 `pending`，把 P04–P07 标记为跳过，运行置为 `CANCELLED` 并记录原因，释放独占锁，关闭决策卡，追加 `rejected` 审计事件。`CANCELLED` 表示「维护者主动取消、没有任何写入」，与表示「部分完成」的 `PARTIAL` 区分开，取消 MUST NOT 用 `PARTIAL` 表达。拒绝时 MUST NOT 有任何写入副作用：错题观察池、分歧表、知识库与技能目录都不得改变。

#### Scenario: 取消本次写入
- **WHEN** 用户对等待审批的运行选择取消
- **THEN** 没有任何写入发生，准入会话回到 `pending`，独占锁被释放，错题观察池与分歧表没有新增记录

### Requirement: fail-run 契约
任一节点抛出异常时，系统 SHALL 把该节点置为 `FAILED` 并记录原因，把其后所有未执行节点显式置为 `SKIPPED`，运行置为 `FAILED`，把准入会话全部恢复为 `pending`，释放独占锁，追加 `run_failed` 审计事件并落失败回执；飞书通道启用时 MUST 推送异常告警。

#### Scenario: P04 首项写入失败
- **WHEN** P04 中某项写入被门禁拒绝并抛出异常
- **THEN** P04 为 `FAILED`，P05–P07 为 `SKIPPED`，运行为 `FAILED`，准入会话回到 `pending`，锁已释放

### Requirement: P04 受控写入
P04 SHALL 只处理被批准的写入项：知识文档经写入链路落盘；规则经确定性归一化后注册；Skill 项在 `SKILL_WRITE_ENABLED` 关闭时记为跳过，否则经 Skill 写入校验并登记技能资产。P04 MUST 汇总写入回执作为节点载荷。

P04 SHALL 在处理写入项之前把 P02 的错题候选写入错题观察池、把分歧候选写入分歧表，每次写入前 MUST 校验独占锁。新注册的规则带观察记录标识或根因键时，MUST 把对应的观察记录置为已晋升并记录被晋升的规则标识。

已批准的知识文档 MUST 有 `relative_path`，写入目标类型 MUST 是受支持的类型；不满足时 MUST 显式报错终止本轮，不得静默跳过。整批知识文档写完后 MUST 只重建一次检索索引，而不是每篇文档重建一次。本轮写入中途失败时，已写下的回执与已写路径 MUST 记录在 P04 节点载荷里，再按 fail-run 契约结束。

#### Scenario: Skill 写入安全阀关闭
- **WHEN** `SKILL_WRITE_ENABLED` 关闭且计划含 Skill 项
- **THEN** 该项回执为 SKIPPED_BY_SAFETY_VALVE，不写任何技能文件

#### Scenario: 候选在审批后才落库
- **WHEN** 本轮有错题候选与分歧候选且审批放行
- **THEN** 观察池与分歧表各新增对应记录，节点载荷给出落库数量

#### Scenario: 新规则回连观察记录
- **WHEN** 本轮注册的新规则带根因键，且观察池里有同一根因键的记录
- **THEN** 该观察记录状态变为已晋升，并带上被晋升的规则标识

#### Scenario: 缺路径的知识文档显式报错
- **WHEN** 已批准的知识文档没有 `relative_path`
- **THEN** P04 为 `FAILED`，错误信息写明缺少 `relative_path`

#### Scenario: 未知写入目标显式报错
- **WHEN** 已批准的写入项的目标类型不受支持
- **THEN** P04 为 `FAILED`，错误信息写明该目标类型

#### Scenario: 整批只重建一次索引
- **WHEN** 一批计划里有多篇知识文档
- **THEN** 检索索引只重建一次

#### Scenario: 中途失败留下部分回执
- **WHEN** 写入第二篇知识文档时抛出异常
- **THEN** P04 节点载荷里留下已写下的回执与已写路径，并记录失败原因

### Requirement: P05 结算
P05 SHALL 把本次真正审查过的准入会话结算为 `processed`，其中 P02 判定为不值得沉淀（`worthy` 为假）的会话结算为 `archived`；本次没有被审查的准入会话 MUST 退回 `pending`，等待下一批。被结算会话的待复盘项 MUST 在本轮关闭并挂上本轮运行标识；被退回会话的待复盘项 MUST 保持开启。阶段含周复盘时执行周五蒸馏；每次结算后 MUST 重建核心索引卡。

#### Scenario: 不值得沉淀的会话归档
- **WHEN** 某准入会话在 P02 被判定 `worthy` 为假
- **THEN** P05 把该会话置为 `archived`，其余被审查过的准入会话置为 `processed`

#### Scenario: 未审查的会话退回队列
- **WHEN** 某准入会话本次没有被送进审查
- **THEN** P05 把该会话置为 `pending`，并在节点载荷里给出退回的会话列表

#### Scenario: 结算关掉本会话的待复盘项
- **WHEN** 本轮结算了某会话，且该会话有开启中的待复盘项
- **THEN** 这些待复盘项被关闭并挂上本轮运行标识，节点载荷给出关闭数量

### Requirement: P06 报告与 P07 交付
P06 SHALL 生成运行摘要（处理对话数、沉淀笔记、新增规则、Skill 变更、核心索引卡状态及各节点结果）。P07 SHALL 按配置执行交付，随后把运行置为 `PASS`、释放独占锁、把决策卡置为完成、追加 `run_completed` 审计事件并落最终回执。

#### Scenario: 交付完成后释锁
- **WHEN** P07 交付执行完毕
- **THEN** 运行状态为 `PASS`，`lock_released` 为真，并写入 `run_completed` 审计事件

### Requirement: 阶段解析
触发阶段为 `auto` 时，系统 SHALL 按东八区时间判定：周五解析为 `both`（每日 + 周复盘），其余日期解析为 `daily`；`friday_weekly_enabled` 关闭时 `both` MUST 降为 `daily`。

#### Scenario: 非周五的自动阶段
- **WHEN** 东八区时间为非周五且触发阶段为 `auto`
- **THEN** 运行阶段解析为 `daily`

### Requirement: 无法归属项目的知识文档处理
当某项 `knowledge_doc` 计划的路由结论为不写入（含 T5 归一化返回"无法归属"）时，系统 SHALL 不为它生成写入：

- P03 MUST 把该项移出写入计划，在节点摘要中给出数量与原因分布，并在节点载荷与 `planned_doc_unrouted` 审计事件中列出标题、原路径、来源会话、原因码、模型声明与证据命中；
- 运行不得因此失败或挂起；移除后计划为空时按"无写入计划"继续；
- P04 再次遇到时 MUST 写入状态为 `SKIPPED_UNROUTED_PROJECT` 的回执（带原因码）并继续处理其余写入项，节点摘要给出跳过数量。

#### Scenario: 无法归属的笔记不落库也不阻断
- **WHEN** 一批计划中有两项知识文档无法归属项目，其余计划正常
- **THEN** 运行状态为 `PASS`，这两项未写入，存在 `planned_doc_unrouted` 审计事件，且 P03 摘要给出数量 2

#### Scenario: 计划全部无法归属
- **WHEN** 本批全部知识文档都无法归属项目，且没有其他写入项
- **THEN** 写入计划为空，运行照常完成后续节点

#### Scenario: 声明与证据冲突留痕
- **WHEN** 模型为某篇知识文档声明项目 beta，而来源会话工作区命中项目 alpha
- **THEN** 该笔记不写入，`planned_doc_unrouted` 审计事件中它的原因码为 `workspace_mismatch`，并列出声明与工作区命中

#### Scenario: 无归属声明保留理由
- **WHEN** 模型声明某篇知识文档无归属并给出理由
- **THEN** 该笔记不写入，审计事件中它的原因码为 `declared_none` 并保留该理由

#### Scenario: 模型计划缺声明不写入
- **WHEN** 模型执行器的某项知识文档计划没有路由声明
- **THEN** 该笔记不写入，原因码为 `declaration_missing`

### Requirement: 批准与取消的原子认领
批准一个等待审批的运行时，系统 SHALL 在同一个写事务内完成：写入或续期锁行（含新鲜的心跳时间）、认领、写入被批准的项、把提问卡置为已决定并记录所选选项（版本加一）、追加审计事件。写入或续期锁行指锁空闲、已过期、有效期为空，或属于本运行（刷新有效期与心跳）时成功；其他运行持有未过期的锁即为失败。认领指把运行从 `AWAITING_APPROVAL` 改为运行中，MUST 只在运行仍处于等待审批时成功。任一步失败时系统 MUST 回滚整个事务，运行、锁与提问卡保持原状，并拒绝本次批准。事务提交后系统 MUST 以库内状态为准，不得用事务前读到的运行对象覆盖它。

认领 MUST 能向调用方区分三种结果：已认领；锁被其他运行占用（并给出锁的到期时间）；运行已不在等待审批。运行进入终态（失败、取消、完成）MUST 经同一个入口、以先写终态后释锁的同一个事务形状落库：带条件的运行状态更新影响 1 行才继续，同一事务内写提问卡状态与结果摘要、审计事件并删除本运行的锁行。提问卡的状态或所选选项每次变化 MUST 使版本加一。运行保存 MUST 拒绝用非终态状态覆盖已是终态的运行。

取消 MUST 用同一认领原语，在同一个写事务内把运行改为 `CANCELLED`、把准入会话恢复为 `pending`、把 P04–P07 置为跳过、写入完成标记与原因、释放本运行的锁、关闭提问卡并追加审计事件；取消不需要取得锁，MUST NOT 删除其他运行的锁行。

批准与取消的审计事件 MUST 记录来源渠道（取值为门户或飞书）；锁是重新取得而不是连续持有的，MUST 在审计事件中标明。

#### Scenario: 并发批准只生效一次
- **WHEN** 两个调用方同时批准同一个等待审批的运行
- **THEN** 只有一方执行 P04–P07，`approved` 审计事件恰有一条，另一方被拒绝

#### Scenario: 批准与取消并发
- **WHEN** 一方批准、另一方取消同一个等待审批的运行
- **THEN** 只有一方生效，会话状态与锁与生效的一方一致，不存在另一方的审计事件

#### Scenario: 独占锁被占用时批准被拒而取消不受影响
- **WHEN** 另一个运行持有未过期的独占锁，此时一方批准、另一方取消同一个等待审批的运行
- **THEN** 批准被拒绝且运行与提问卡不变；取消照常生效，那个运行持有的锁保持不动

#### Scenario: 认领失败时锁保持原状
- **WHEN** 一个运行已被另一方批准、不再处于等待审批，此时再次批准它
- **THEN** 整个事务回滚，锁与运行保持原状，本次批准被拒绝

#### Scenario: 挂起近一小时后批准
- **WHEN** 一个运行挂起 59 分钟后被批准
- **THEN** 认领成功，锁的有效期被刷新，审计事件标明锁为连续持有，执行期间启动新运行被拒绝

#### Scenario: 批准来源留痕
- **WHEN** 一次批准或取消生效
- **THEN** 对应审计事件的载荷记录来源渠道

### Requirement: 独占锁续期与执行心跳
取锁 MUST 只有一个实现，其可取条件以「批准与取消的原子认领」的定义为准；启动运行与批准认领 MUST 共用它，且取锁 MUST 同时写入心跳时间。启动运行取锁失败时 MUST 抛出锁冲突异常、不创建运行记录、不写审计。

心跳覆盖从取锁（或认领）到运行终态的全程：心跳线程 MUST 在取锁或认领提交后启动、在挂起返回前与终态释锁前停止；挂起期间 MUST NOT 续期。执行期间系统 MUST 至少每 15 秒续期一次，并在每个副作用之前做同步续期检查（P04 每写入一项之前、P05 每个会话结算之前、P07 交付之前），以续期更新的行数为准；行数为 0 且不是自己刚释放的锁时，系统 MUST 停止后续写入，按 fail-run 契约结束运行，并注明执行期间失去独占锁。续期抛出的异常 MUST NOT 使心跳线程退出。

#### Scenario: 长时间执行期间锁不过期
- **WHEN** 一次运行的 P04 持续超过 30 分钟
- **THEN** 期间启动新运行被拒绝，运行结束后锁被释放

#### Scenario: 过期锁上的竞争
- **WHEN** 锁已过期，批准认领与启动新运行同时到达
- **THEN** 只有一方取得锁，另一方被拒绝

#### Scenario: 执行期间失去锁
- **WHEN** 运行执行期间锁被其他运行取得
- **THEN** 该运行在下一次同步续期检查后置为 `FAILED`，审计事件注明执行期间失去独占锁

#### Scenario: 挂起返回后心跳停止
- **WHEN** 一次运行在审批门挂起并返回
- **THEN** 心跳线程已停止，锁的有效期不被刷新，挂起超过有效期后锁可被其他运行取得

### Requirement: 收尾没有执行者的运行
`serve` 启动时及之后每 30 秒，对状态为运行中、而心跳为空或已停止刷新超过 5 分钟的运行，系统 SHALL 按 fail-run 契约收尾：失败节点取第一个未终结的节点（全部节点已终态时在审计中注明没有失败节点），审计事件与提问卡注明执行被中断。收尾 MUST 经终态入口的条件更新执行，影响 0 行即跳过；心跳仍在刷新的运行 MUST 不受影响。被收尾的运行若执行者仍在，它 MUST NOT 再改动会话状态，只能把运行推向失败。

#### Scenario: 执行中崩溃后重启
- **WHEN** 一次运行执行到 P04 中途时 `serve` 被强制结束，随后 `serve` 重新启动，心跳已停止刷新超过 5 分钟
- **THEN** 该运行置为 `FAILED`，P04 为 `FAILED`、P05–P07 为 `SKIPPED`，其准入会话回到 `pending`，提问卡状态为执行失败

#### Scenario: 运行期间发现执行者消失
- **WHEN** 一次运行的执行进程在没有停止 `serve` 的情况下消失，心跳停止刷新超过 5 分钟
- **THEN** 之后的一次检查把它按 fail-run 契约收尾

#### Scenario: 其它进程正在执行的运行不受影响
- **WHEN** `serve` 启动时有一个运行由另一个仍在刷新心跳的进程执行
- **THEN** 该运行不被改动

#### Scenario: 收尾只执行一次
- **WHEN** 收尾与被中断执行者的收尾同时到达，或两个 `serve` 进程同时收尾
- **THEN** 只有一次收尾生效，审计与告警各只有一份

### Requirement: 提问卡状态与运行终态一致
运行状态与提问卡状态的对应关系 SHALL 由对账维护：`PASS` 对应已完成，`PARTIAL` 对应已关闭，`CANCELLED` 对应已关闭，`FAILED` 对应执行失败；运行中不动；仍在等待审批的运行，提问卡不是待决时校正回待决并清空已决定时间与所选选项。没有提问卡的运行 MUST 不被凭空造卡。每次校正 MUST 是一条同时核对运行状态的更新，并使提问卡版本加一、留审计。

#### Scenario: 批准后运行失败
- **WHEN** 批准生效后某个节点失败
- **THEN** 提问卡状态为 `failed`，结果摘要含失败节点

#### Scenario: 旧的已决定卡片被校正
- **WHEN** `serve` 启动时库里有一张提问卡停在已决定，而对应运行的状态是 `FAILED`
- **THEN** 这张提问卡被校正为 `failed`，版本加一，并存在说明校正的审计事件

#### Scenario: 等待审批而卡片非待决
- **WHEN** 一个运行仍处于等待审批，而它的提问卡不是待决
- **THEN** 提问卡被校正回待决，已决定时间与所选选项被清空，版本加一

#### Scenario: 无提问卡的运行
- **WHEN** 对账遇到一个已终态但没有提问卡的运行
- **THEN** 不创建提问卡，状态不变

#### Scenario: 对账期间发生批准
- **WHEN** 对账读取运行与校正提问卡之间，另一个调用方完成了批准
- **THEN** 校正语句因运行状态已变为运行中而不生效，提问卡保持已决定

### Requirement: 模块化流水线包与兼容门面
P00–P07 的实现 MUST 位于 `backend/ai_flywheel/core/pipeline/`，并按职责拆分：节点常量与错误（`constants`）、事件总线（`events`）、候选归一化与路由辅助（`helpers`）、心跳、锁检查点与终态路径（`recovery`）、阶段序列（`coordinator`）、可选的本地 Git 提交（`git_commit`）。

`backend/ai_flywheel/core/orchestrator.py` MUST 保留为兼容门面，且少于 100 行。`WorkflowOrchestrator`、`EventBroker`、`WorkflowLockError`、`ApprovalLockBusy`、`LockLostError`、`NODE_TEMPLATES`、`PLAN_SOURCE_LABELS`、`REVIEW_SOURCE_LABELS` 与 `commit_p04_written_files` MUST 从该门面导入成功，且 MUST 与从 `core/pipeline/*` 导入的是同一对象。

流水线 MUST 在调用时经该门面解析可替换协作者（`build_runner`、`run_dream_consolidation`、`rebuild_core_card`），使既有对门面模块属性的替换继续作用到流水线。

拆分 MUST NOT 改变任何阶段的副作用边界、独占锁不变量、心跳检查点与 fail-run 契约。

#### Scenario: 旧导入路径解析到同一对象
- **WHEN** 既有代码从 `ai_flywheel.core.orchestrator` 导入编排器、事件总线、节点表或错误类型
- **THEN** 导入成功，且对象与从 `ai_flywheel.core.pipeline.*` 导入的是同一个

#### Scenario: 门面上的协作者替换仍然生效
- **WHEN** 测试替换 `ai_flywheel.core.orchestrator.build_runner` 后启动一次运行
- **THEN** P02 使用被替换的执行器，替换前的导入方式与替换点都不需要改动

#### Scenario: 阶段副作用边界不变
- **WHEN** 拆分后运行一次带错题候选与分歧候选的批次
- **THEN** P02 仍只把候选留在节点载荷里，P04 才落库；失败批次的准入会话回到 `pending` 且独占锁已释放

### Requirement: P04 可选的写入后本地 Git 提交
当 `knowledge_sink.auto_git_commit` 为真时，P04 SHALL 在本批写入全部校验通过后，把本批写出的知识文档与 Skill 文件提交到它们所在的本地 Git 仓库。提交 MUST 按仓库根分组，且每次只暂存并提交本批写出的路径（`git add -- <paths>`、`git commit --only -- <paths>`）；MUST NOT 使用 `git add -A` 或 `git add .`，MUST NOT 改动同一工作区的其它已修改或未跟踪文件，MUST NOT 执行 `git push`。

仓库已配置的 `user.name` / `user.email` MUST 被保留；仅当仓库与全局配置都没有身份时，才使用中性回退身份。提交信息 MUST 含 `run_id`、审批来源与本次提交的相对文件清单。

提交成功后 MUST 追加 `p04_git_commit` 审计事件并把结果写入 P04 节点载荷；本批写入路径不在任何 Git 仓库内时 MUST 追加 `p04_git_commit_skipped`；Git 缺失或提交失败时 MUST 追加 `p04_git_commit_failed`。任何 Git 侧结果 MUST NOT 回滚已通过校验的写入，也 MUST NOT 使运行失败。该配置默认为假。

审批来源 MUST 取自批准认领事务写入的审计事件（门户或飞书）；未挂起、自动放行的批次记为 `auto`。

#### Scenario: 默认关闭不产生提交
- **WHEN** `auto_git_commit` 保持默认假，在 Git 仓库内完成一次写出知识文档的 P04
- **THEN** 仓库的提交数不变，文档留在工作区且未被暂存，P04 节点载荷没有 Git 提交结果

#### Scenario: 开启时只提交本批写入的文件
- **WHEN** `auto_git_commit` 为真，工作区同时存在一个已修改的已跟踪文件与一个未跟踪文件
- **THEN** 恰好多出一个提交，该提交只包含 P04 写出的文件；已修改的已跟踪文件仍未提交，未跟踪文件仍未跟踪

#### Scenario: 提交信息可追溯
- **WHEN** 一次开启自动提交的批次完成
- **THEN** 提交主题为 `flywheel(p04): <run_id> (<N> file(s))`，正文含 `run_id`、`approval_source` 与相对文件清单，且存在 `p04_git_commit` 审计事件

#### Scenario: 仓库外路径留痕且不阻断
- **WHEN** `auto_git_commit` 为真，而知识落点不在任何 Git 仓库内
- **THEN** 追加 `p04_git_commit_skipped` 审计事件，P04 载荷的提交状态为 `skipped`、原因为 `not_a_git_repo`，运行仍以 `PASS` 结束

#### Scenario: Git 侧失败不失败批次
- **WHEN** Git 可执行文件缺失或提交命令失败
- **THEN** 追加 `p04_git_commit_failed` 审计事件，已通过校验的写入保持不变，运行不因 Git 失败而失败
