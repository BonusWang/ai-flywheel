## Context

P03 已把通用草稿归一化为项目实战卡，并把最终路径和内容持久化在 `WorkflowRunRecord`。
P04 在审批后重新路由并调用知识落点写入器。现有写入器已经具备临时文件替换、回读、D2 后检和
失败恢复能力，但事务只覆盖主卡。项目笔记索引位于同一项目目录，必须成为审批时可见的派生写入。

## Goals / Non-Goals

**Goals:**

- 主卡、项目索引、审批预览、P04 回执与 D2 `--write-set` 描述同一组物理路径。
- 并发只影响同一项目索引的写入顺序，不丢失不同卡片的条目。
- 失败、重试和旧计划均不会留下孤儿卡、重复条目或未批准的索引变更。

**Non-Goals:**

- 不自动重排人工维护的索引分区，也不改写受控词表或历史条目。
- 不把项目索引加入 `index-索引.md`，项目索引仍是实战卡登记面。
- 不新增配置键、数据库迁移或通用文件数据库事务。

## Decisions

- **采用独立的自动登记小节。**
  各项目索引结构不同，强行插入某个人工分区会误判问题域。实现仅在缺少同名条目时，向
  `## P04 自动登记` 的固定 Markdown 表插入精确链接。已有条目不重复写入。

- **采用 P03 预览、P04 精确复核。**
  P03 把 `kind / target_path / action / status / entry_preview` 写入计划项并持久化。P04 在目标
  索引锁内按最新文件重新规划，要求目标、动作和条目与已批准记录完全一致。旧计划若现在需要新增
  但没有批准记录，失败关闭。

- **物理写入预算按去重路径计算。**
  路径集合包含主卡与需要新增条目的项目索引，同一索引被多张卡共用时只计一次，总数不得超过
  `knowledge_sink.max_write_set`。已存在条目不增加物理路径。

- **采用锁内读改写和补偿回滚。**
  索引锁使用同目录 `O_EXCL` 锁文件，跨线程和 Flywheel 进程串行化。写入顺序为索引、主卡；
  任一后续步骤失败则恢复索引和主卡 preimage，再以两条路径重跑一次跳过校验器的索引同步。

- **D2 后检接收 CSV write-set。**
  项目索引与主卡同时进入 `--write-set`，后检能够核对链接可见性与派生登记面。证据 JSON 的
  `practice_index` 字段记录目标、条目、前后 SHA-256 和最终状态。

- **P04 在数据库副作用前做批准范围预检。**
  错题观察池、分歧和知识文件的写入都晚于物理集合复核，防止越权或超限计划留下半批数据库副作用。

## Risks / Trade-offs

- 自动登记小节位于人工索引之后 → 索引仍需人工按需归并到问题域；本次优先保证可检索、可追溯和不丢数据。
- 锁等待默认只有 5 秒 → 活跃冲突会显式失败并可重试，不会无限挂起流水线。
- 历史待审批计划没有副作用字段 → 部署后需要重新规划审批，这是避免未授权派生写入的必要兼容边界。

## Verification

- `pytest` 覆盖重卡、轻记卡、重复执行、共享索引并发、旧计划失败关闭、索引消失、双路径门禁回滚、
  Feishu 审批预览和 P04 物理预算。
- 沙箱章节使用真实临时目录与真实文件写入，验证两张卡进入同一索引、第二次执行不重复、
  失败后两处 preimage 均恢复。
- `python scripts/verify_repo.py --frontend` 作为仓库级门禁。
