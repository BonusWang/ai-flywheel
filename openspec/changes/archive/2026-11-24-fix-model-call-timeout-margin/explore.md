### 2.2 耗时去向（real）

| 假设 | 判定 | 依据 |
|---|---|---|
| 网关排队 | 不是主因 | 同一模型其他客户端的流式调用：首 token 延迟中位 1–5 秒，p90 不超过约 10 秒。飞轮自己最小的一次调用（1,850 tokens）共 14.0 秒；按观测到的最快速率（240 tokens/秒）算，生成最多占 7.7 秒，留给排队与首 token 的不超过约 6 秒 |
| 可见输出的长度 | 不是主因 | P03 可见输出 259–2,145 tokens，占输出 tokens 的 6–21%（最近五次 6–13%）；P02 可见输出 2,525–4,751 tokens |
| 输入长度 | 不是 | 输入 2.6k–18k tokens。P03 的输入多数只有 P02 的一半以内，可见输出更少，耗时却与 P02 相当，差别在推理量 |
| 模型本身：推理 tokens 与解码速率 | 主因 | 推理占 P03 输出的 79–94%、P02 的 68–87%；每次调用的耗时都等于 tokens 除以当次速率 |

解码速率（14 次成功调用）：最慢 106，p10 113，中位 144，p90 197，最快 240（tokens/秒）。阈值换算成 token 预算：

| 解码速率 | 120 秒 | 240 秒 | 480 秒 |
|---|---:|---:|---:|
| 106（最慢实测） | 1.27 万 | 2.54 万 | 5.09 万 |

| 197（p90） | 2.36 万 | 4.73 万 | 9.46 万 |

迄今最大的几次调用：

| 调用 | 输出 tokens | 当次速率与耗时 | 按 p10 速率（113） | 按最慢速率（106） |

### 2.4 提示词变长的增量归因（real）

同一批次的两种提示词（2026-11-24 #1 的真实运行用原提示词；叠加「逐项字段契约」与「按挂载合同路由」后的沙箱单次调用）：

| 项 | 原提示词 | 逐项字段契约 + 按挂载合同路由 | 增量 |
|---|---:|---:|---:|
| 输入 tokens | 3,320 | 4,127 | +807 |
| 推理 tokens | 19,045 | 23,922 | +4,877 |
| 可见输出 tokens | 1,516 | 1,657 | +141 |
| 解码速率（tokens/秒） | 143 | 144 | 持平 |
| 耗时 | 143.8 s | 177.5 s | +33.7 s |

两次的速率几乎相同：多出的 4,877 个推理 tokens 按当次速率约 34 秒，与实测多出的 33.7 秒相符。可见输出只多了 141 tokens，约 1 秒。两项变更各贡献多少推理量，这两个样本分不开；`feat-p03-wiki-contract-routing` 的 evidence 第 6 节把这一段增量记为「无法单独归因」，能确定的部分是：增量落在推理上，不在可见输出上。

### 2.5 代码与配置现状（static）

| 事实 | 位置 | 影响 |
|---|---|---|
| 非流式请求；`timeout_seconds` 是整次调用的墙钟上限 | `runners.py` `_call_chat_completion` | 生成时间随 tokens 线性增长，阈值却是固定的 |
| 请求体只有模型、消息、温度；没有推理强度，也没有输出上限 | 同上 | 推理强度取上游默认值 |
| 响应里的用量与实际服务模型被丢弃 | 同上 | 运行记录里没有 token 用量，查耗时要翻网关日志 |
| 只有「畸形 JSON 重试一次」；超时与连接错误不重试 | `_invoke_api` | 一次超时等于整批失败 |
| 格式修复是第二次完整调用，各自适用同一阈值 | `_invoke_api` | 一个节点的最坏耗时本来就是阈值的 2 倍 |
| 主调用抛出的异常原样抛到编排器，节点错误只记异常原文 | `_invoke_api` 主调用、`orchestrator.py` `_fail_run` | 超时只有 `timed out`，不含阶段、阈值、尝试次数，排障要靠网关日志；HTTP 错误的原文带完整请求地址（test：本地构造 502 响应验证） |
| 格式修复那次调用抛出的异常被吞掉，按「修复后仍不是 JSON」处理 | `_invoke_api` 修复分支的 `except Exception` | P02：诊断记下异常类型（`repair_error`），失败信息写「格式修复的调用没有完成（ReadTimeout）」，原因码仍是原回复的 `UNPARSABLE_REPLY`（`fix-p02-silent-review-fallback` 补的留痕）。P03 不传诊断，修复调用超时仍只显示「计划不可用」，看不出是超时，由本变更处理 |
| 失败后准入会话退回 `pending`；成功调用的输出已缓存，重跑时 P02 成功过就只重做 P03 | `_fail_run`、输出缓存 | 超时的那次调用没有缓存，重跑同一批要重新面对；是否再超时取决于当次的推理量与速率（推断） |
| 示例配置的 API 超时是 120 秒，代码默认是 240 秒 | `flywheel.yaml.example`、`config.py` | 照抄示例就是出过超时的那个阈值 |

## 3. 选项与取舍

| 选项 | 能解决什么 | 代价 | 对现有行为契约的影响 | 证据 | 判断 |
|---|---|---|---|---|---|
| 1 调大超时（240 → 480 或 600 秒） | 覆盖 2–2.5 倍的时间：480 秒在 p10 速率下可容纳 5.4 万 tokens，按 16:31 当段的 112 tokens/秒也是 5.4 万。2026-11-24 #3 那次要多少才够：unknown | 失败要等更久才暴露，期间一直持锁；治标：推理继续变长时还会再撞上，也不让运行变快 | 无。只改配置、示例与说明；fail-run 契约不变 | 速率与 tokens 分布（real） | 可作兜底层，单独用不够 |
| 2 压缩 P03 输出 | 上限是可见输出那部分：按最大的一次算是 11–16 秒（6–9%）；砍一半只省 5–8 秒 | 知识文档正文与 Skill 更新内容变短，影响落盘质量；与「Skill 更新不丢内容」的在途方案相冲 | 改 `计划输入与提示词`（正文 220–450 字符）；单批上限已经是 5 | 可见输出占比（real） | 不为超时做 |
| 3 P03 拆成两次调用 | 单次调用的 tokens 上限变小 | 推理总量不一定降：两次各读一遍输入、各想一遍。串行则总时长增加，并行则要改节点执行方式。另有两个超时点、两份缓存、各一次格式修复，5 个名额在两次之间怎么分要重新定义 | 大：`计划输入与提示词`、`输出缓存与格式修复`、`计划来源唯一` 都要改，并叠在两个在途的 P03 变更之上 | 推理占比（real）；拆分后推理量：unknown | 不为超时做 |
| 4 超时后重试 | 应对随机性：推理量与速率都在波动，重来一次有相当机会通过 | 最坏耗时翻倍，持锁更久；网关把被放弃的那次记为已取消，上游是否真的停止生成 unknown；对「批次本身太重」无效，只是晚一点失败 | `输出缓存与格式修复` 目前只允许畸形 JSON 重试一次，要新增超时重试；fail-run 契约不变，重试用尽才失败；诊断要记尝试次数 | 超时已发生 2 次（120 秒、240 秒阈值各 1 次）；P03 推理量随批次在 0.94 万–2.39 万之间、速率 106–240（real）；重试成功率：unknown | 建议做：1 次，不退避 |
| 5 降低推理强度（新增） | 直接作用于主因（推理占 79–94%）。旁证：同模型同接口的其他调用方，低强度的推理强度中位约为最高强度的 1/3，p90 约 1/6（任务不同，不是对照） | 审查与计划质量可能下降（JSON 合法性、路由声明、摘要），需要对照实测；多一个配置项；部分 OpenAI 兼容端点不认识该参数会返回 400，所以默认不发送、显式开启 | 不改 P02 / P03 的输出契约；新增请求参数配置；缓存键要把该参数算进去 | 推理占比（real）；降强度后的效果：unknown，需实测 | 建议作为主方案，先实测 |
| 6 换模型（新增，只改本地配置） | 同属「模型本身」。网关上可选的模型里，当前模型解码最快（其他客户端的调用中位约 150 tokens/秒）但推理重；另一款 Flash 模型推理占比约 20%、解码中位约 107 tokens/秒 | 输出质量与契约遵从度未知，需要实测；模型由维护者在本地配置里选 | 无 | 各模型的速率与推理占比（real，其他任务的调用） | 作为选项 5 的备选，放进同一次实测 |
| 7 改为流式请求（新增） | 超时从「整次调用多久」变成「多久没有新 token」，慢但在推进的调用不会被打断；顺带能记录首 token 延迟 | 仍需总时长上限兜底；要解析流，改动缓存与重试路径；不减少耗时 | `timeout_seconds` 的含义变了，要新增配置项 | test：本地复现里 1 秒超时没有打断持续 3 秒的分块响应 | 不在本次做 |

关于退避：超时不是限流。等一会儿不会让下一次更快，退避只是延长持锁时间，所以重试 1 次、不等待。

## 4. 推荐做法

主方案取决于对照实测的结果，所以先实测、再实施。

| 步骤 | 内容 | 前置条件 |
|---|---|---|
| 实测 | P02 用 2026-11-24 #3（超时的那一批）的提示词：「当前请求」臂把客户端等待放宽到 600 秒，量出这一批到底要多久、生成多少；再做一次「低推理强度」。P03 用 2026-11-24 #1 的（迄今最大的 P03）：当前请求 1 次、低强度 2 次。重建的提示词与当次不完全相同（复盘线索清单随时间变化），所以「当前请求」臂就是基线 | 维护者授权（5.1） |
| 主方案 | 推理 tokens 降幅达到一半以上且输出质量过关：新增请求参数配置（默认不发送），本地配置里设为低强度 | 实测 |
| 兜底 | 超时与连接失败重试 1 次，不退避；最坏耗时因此翻倍 | 无 |
| 留痕 | 每次调用把输入、输出、推理 tokens，实际服务模型，耗时与尝试次数写进节点载荷 | 无 |
| 阈值 | 降强度成立：保持 240 秒，用实测的 tokens 按第 2.2 节重算预算，余量够就不动。降不成立：调到 600 秒 | 实测 |
| 对齐 | 示例配置的 API 超时改成与代码默认一致（120 → 240） | 无 |

## 5. 需要维护者决定

### 5.1 是否授权对照实测

| 选项 | 内容 | 代价 |
|---|---|---|
| A 授权（建议） | 2 次探针，各 1 token，只发一句固定的话；P02 两次（2026-11-24 #3 批次，其中「当前请求」臂最多等 600 秒）、P03 三次（2026-11-24 #1 批次），发的是这两批的会话正文前 3000 字符、会话摘要、复盘线索摘要、Wiki 项目名与 Skill 名单；实施后再用真实执行器验证 1–2 次。合计 7–9 次，预计 25–35 分钟 | 内容类别与日常运行相同；只调用模型，不执行写入链路，不碰真实知识库与运行库 |
| B 不授权 | 按「调大超时到 600 秒 + 超时重试 1 次 + 留痕」实施 | 推理强度与换模型两条路保持 unknown；运行不会变快，只是多了余量；超时的那一批到底需要多久仍是 unknown |

实测的判定口径：

| 项 | 过线条件 |
|---|---|
| 降强度是否成立 | 同一提示词下输出 tokens 降幅不低于 50% |
| P02 质量 | JSON 对象，四个列表齐全，发现条数与当前请求相当，`session_key` 都对得上送审的会话 |
| P03 质量 | JSON 可解析；计划项全部保留，每项带来源会话；知识文档的路由声明在候选集内，归属与当前请求一致；Skill 项的目标是现有 Skill |

### 5.2 方向

| 选项 | 组合 | 适用 |
|---|---|---|
| 甲（建议） | 降推理强度 + 超时重试 + 留痕；阈值保持 240 秒 | 实测过线 |
| 乙 | 调大到 600 秒 + 超时重试 + 留痕 | 不实测，或实测不过线 |
| 丙 | 换模型（只改本地配置）+ 超时重试 + 留痕 | 实测里另一模型明显更好 |

授权实测即按这张表走：过线走甲，不过线走乙，不再回头问一次。实测显示另一模型明显更好时，先回报再定是否走丙。

### 5.3 不依赖本变更的止血项

| 做法 | 生效方式 | 依据 |
|---|---|---|
| 把本地配置的 API 超时从 240 秒调到 600 秒 | 在门户的系统设置里提交即生效，并写回配置文件（`PUT /api/site/config`，static）；直接改配置文件则要重启服务 | 16:31 那次按 112 tokens/秒，240 秒只够约 2.6 万 tokens；600 秒够约 6.7 万。是否够 unknown，但已覆盖迄今观测到的全部速率与生成量 |

这是本地配置，不属于本变更。默认值是否随实测调整，见 5.2。

## 7. 规格落点与并发依赖

- 规格建议新建能力 `model-call-reliability`（模型调用可靠性）：先补现状基线（墙钟超时、不重试、不记用量），再写增量。不改 P02 / P03 契约里「格式修复只重试一次」的要求，也就不用叠在在途变更的增量文本上。
- `fix-p02-silent-review-fallback` 的代码已于 2026-11-24 落到工作区，不再修改 `runners.py` 与 `orchestrator.py`。它给 `_invoke_api` / `_invoke_cli` 加了可选参数 `reply_trace`（记录回复长度、是否做过格式修复、解析错误、修复调用的异常类型），并删掉了执行器的 `self.fallback`。
- 仍在修改这几个文件的在途变更：`feat-feishu-approval-card-loop` 与 `fix-approval-claim-and-recovery`（`orchestrator.py`、`config.py`），`feat-skill-lossless-update`（`runners.py` 的提示词与归一化）。本变更的代码改动排在这些变更落定之后；排到之前只做规格。
- 对本变更实现的约束（static）：
  - 重试放在单次 HTTP 调用（`_call_chat_completion`）这一层，主调用与格式修复调用都适用，`reply_trace` 的写入点不用挪；重试用尽后抛同类型的异常，`repair_error` 的记法不变；
  - 留痕只记异常类型名，不记异常原文：HTTP 错误的原文带请求地址；
  - 用量与实际服务模型的回传不改 `_call_chat_completion` 的签名与返回值，因为沙箱回放用返回字符串的桩替换它；
  - API 模式下跑编排器的用例，P02 桩回复至少带一条 `findings`（P02 的新契约）。

## 8. 不在范围与暴露的问题

| 项 | 说明 |
|---|---|
