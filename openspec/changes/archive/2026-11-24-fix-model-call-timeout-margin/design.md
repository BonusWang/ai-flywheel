# Design：模型调用可靠性

> 2026-11-25。证据分级：real = 真实数据（只读运行库、模型网关的请求日志）；test = 自动测试或本地复现；
> static = 静态判断（读代码）；unknown = 未验证。本页已脱敏：不含个人绝对路径、会话键、网关地址与路由组别名。

## 1. 耗时模型：几乎全部在生成 token 上

16 次调用的耗时 ≈（推理 tokens + 可见输出 tokens）÷ 解码速率。解码速率在 106–240 tokens/秒之间波动（14 次成功调用，中位 144），因此 240 秒对应的 token 预算在 2.5 万–4.7 万之间浮动。

| 调用 | 输出 tokens | 当次速率与耗时 | 按最慢实测速率（106） |
|---|---:|---|---|
| P03，沙箱单次调用 | 2.56 万 | 144 tokens/秒，178 秒 | 241 秒，超时 |
| P02，2026-11-24 #2 | 2.18 万 | 112 tokens/秒，195 秒 | 205 秒 |
| P02，2026-11-23 #9 | 2.49 万 | 195 tokens/秒，128 秒 | 235 秒（余量 2%） |

**结论**：墙钟阈值固定，生成量浮动。一次超时往往是「这一批比平时重」而不是「服务坏了」——16:31 那次超时的请求在途的 240 秒里，同一模型的其他 5 次调用全部完成，前后 22 分钟内同一模型 35 次调用全部完成。

## 2. 决策：传输失败重试 1 次，不退避

| 方案 | 能解决什么 | 代价 |
|---|---|---|
| 调大超时（240 → 480 / 600） | 覆盖 2–2.5 倍的时间 | 治标：推理继续变长时还会再撞上；失败要等更久才暴露，期间一直持锁 |
| 压缩 P03 输出 | 只省可见输出那部分（按最大的一次算 11–16 秒） | 砍知识文档正文与 Skill 更新内容，与在途的「Skill 更新不丢内容」相冲 |
| P03 拆成两次调用 | 单次调用的 token 上限变小 | 推理总量不一定降（两次各读一遍输入、各想一遍），另有两个超时点、两份缓存 |
| 传输失败重试 | 应对随机性：推理量与速率都在波动，重来一次有相当机会通过 | 最坏耗时翻倍，持锁更久；对「批次本身太重」无效，只是晚一点失败 |
| 降低推理强度 | 直接作用于主因（推理占输出 tokens 的 79–94%） | 质量可能下降，需对照实测；部分端点不认识该参数会返回 400，所以默认不发送 |

**决定**：本变更实现「重试 + 留痕 + 脱敏摘要 + 可配置的推理强度」。调大超时与降推理强度的效果需要对照实测，本变更只提供能力与默认值，不代替实测。

**为什么重试放在单次 HTTP 调用这一层**：主调用与格式修复调用都适用这一层，重试逻辑写一次；`reply_trace` 的写入点不用挪；重试用尽后抛同类型的异常，格式修复分支的记法不变。

**为什么不退避**：超时不是限流。等一会儿不会让下一次更快，退避只是延长持锁时间。

## 3. 决策：推理强度默认不发送

推理强度是主因（推理占输出的 79–94%），但不是所有 OpenAI 兼容端点都认识这个参数——不认识会返回 400，一次 400 就是整批失败。因此：

- 默认值为空 → 请求 JSON 里不出现该参数 → 与现状完全一致，可移植性不变；
- 显式配置时才发送，并进入缓存键：换了推理强度就是另一个问题，绝不能命中旧回复。

## 4. 决策：留痕只记事实，不记原文

每次调用记录：尝试次数、耗时毫秒、实际服务的模型、输入 tokens、输出 tokens、推理 tokens。

- 推理 tokens 从 `usage.completion_tokens_details.reasoning_tokens` 取，没有就从 `usage.reasoning_tokens` 取，都没有则为缺省。
- 网关不给 `usage` 时留痕缺省，调用照常完成——留痕不是新的失败原因。
- 调用被替换为桩（沙箱回放）时没有留痕，诊断里为缺省，不报错。

**为什么这些字段够用**：耗时 ≈ tokens ÷ 速率。知道 tokens 与耗时，就能判断是「批次太重」还是「速率异常」；知道实际服务的模型，才能发现上游换了模型。

## 5. 决策：失败摘要脱敏，只留可定位的四项

传输失败时节点载荷带：阶段、超时阈值、尝试次数、异常类型。

**不带的**：网关地址（可能带部署的私有主机名）、请求内容、回复内容、异常的原文。HTTP 错误保留状态码——那是最可行动的信息，且不含地址。

**为什么不用异常原文**：本地复现确认错误原文来自客户端读超时，只有 `timed out`；而某些异常（连接错误）的原文可能带主机名。异常类型名足够定位。

## 6. 决策：P03 与 P02 对齐

P02 的审查执行器已经有 `reply_trace`（回复长度、是否做过格式修复、解析错误、修复调用的异常类型）。P03 的计划执行器没有，因此 P03 的计划诊断看不到「模型回了什么形状的东西」——P03 触发格式修复时，故障信息只显示「计划不可用」，看不出是超时。

本次把 P03 对齐到 P02：同样的轨迹进计划诊断，同样的调用留痕进节点载荷。

## 7. 未验证项

| 项 | 说明 |
|---|---|
| 降推理强度的效果 | 未知，需对照实测（输出 tokens 降幅不低于 50%、JSON 合法性与内容质量不过线） |
| 重试的成功率 | 未知：P03 推理量在 0.94 万–2.39 万之间波动、速率 106–240，重来一次能否通过取决于当次运气 |
| 客户端断开后上游是否停止生成 | 网关把被放弃的请求记为已取消；上游是否真的停止生成 unknown，重试时可能与被放弃的那次争用并发额度 |
| 换模型后的契约遵从度 | 未知，只能实测 |
| 最坏耗时翻倍后的持锁时长 | 已知代价：一次批量的最坏墙钟从 240 秒变成 480 秒（主调用 + 一次重试各自适用阈值，格式修复调用同理） |

## 8. 真实验证方式

- **test**：请求体带与不带给定参数；缓存键随参数变化；超时与连接错误各重试一次、HTTP 错误不重试；用量与尝试次数进节点载荷；网关不给用量时不报错；传输失败留下脱敏摘要且不含网关地址。
- **real**：真实执行器在沙箱数据目录上跑一次 P03，节点载荷里的 tokens 与耗时与网关日志对得上；沙箱回放确认超时重试用尽后仍按 fail-run 契约失败。
