## Why

模型调用的耗时几乎全部花在生成 token 上，而墙钟阈值是固定的。已经发生过整批失败。

- **现象**：2026-11-24 16:31 的真实运行，P02 的第一次模型调用在 241 秒处读超时，整轮 `FAILED`、零写入，8 个会话退回 `pending`。更早一次（11-23 19:29）在 120 秒的旧阈值上超时，同样整批失败。两次错误原文都只有 `timed out`。
- **影响**：一次超时等于整批沉淀作废；排障时节点错误只有异常原文，看不出是哪个阶段、阈值多少、试了几次；调用的 token 用量与实际服务的模型被丢弃，查耗时要翻网关日志。更糟的是：请求在途的 240 秒里，同一模型的其他调用全部完成——这次超时不是网关整体故障，是这一批本身太重，而系统对此毫无余量。
- **根因分两层**：
  1. 超时与连接错误不重试。一次随机的读超时等于整批失败，哪怕下一次同样的请求就能过；
  2. 调用过程不留痕。用量、耗时、尝试次数都不进节点载荷，超时与「模型太慢」无法区分。

证据见 [explore.md](./explore.md)：16 次模型调用的网关请求日志与只读运行库（real）、本地超时复现（test）、代码路径（static）。

## What Changes

- **传输失败即时重试**：超时或连接错误按配置立即重试，不退避（超时不是限流，等一会儿不会让下一次更快）。重试次数取 `runner.api.transport_retries`（默认 1，0 关闭）。HTTP 状态错误不重试，仍脱敏为 `Model API returned HTTP <状态码>`。
- **推理强度可配置**：新增 `runner.api.reasoning_effort`。为空时请求 JSON 里不出现该参数（非空时发送），以保持对不认识该参数的 OpenAI 兼容端点的可移植性；非空值进入输出缓存键，改推理强度不会命中旧缓存。
- **调用留痕**：每次调用记录尝试次数、耗时毫秒、实际服务的模型、输入 tokens、输出 tokens 与推理 tokens，并随 P02、P03 的节点载荷暴露。网关不给用量、或调用被替换为桩时，留痕缺省而不报错。
- **失败摘要脱敏**：传输失败时在节点载荷留下阶段、超时阈值、尝试次数与异常类型；不留下网关地址、请求内容与回复内容。
- **P03 与 P02 对齐**：P03 同样把回复轨迹（长度、是否做过格式修复、解析错误、修复调用的异常类型、调用留痕）带进计划诊断，P03 节点载荷同样暴露调用留痕。
- **示例配置与代码一致**：`flywheel.yaml.example` 补齐两个新配置项并写明含义。

## Capabilities

### New Capabilities
- `model-call-reliability`: 模型调用可靠性。请求参数的可移植性、传输失败的即时重试、调用留痕、失败摘要脱敏。本能力此前没有基线规格，以下要求描述本变更落地后的完整行为。

### Modified Capabilities
- `write-plan-contract`: 输出缓存与格式修复。缓存键加入推理强度；计划诊断带上回复轨迹与调用留痕。
- `session-review-contract`: 审查输出缓存与格式修复。缓存键加入推理强度；审查诊断带上调用留痕。

## Impact

- 代码：`adapters/runners.py`（调用、重试、留痕、缓存键、诊断）、`core/orchestrator.py`（节点载荷暴露调用留痕与失败摘要）、`config.py`（两个新配置项）。
- 配置：`flywheel.yaml.example` 增加 `reasoning_effort` 与 `transport_retries`；本地 `flywheel.yaml` 不受影响（缺省即新行为）。
- 测试：新增 `tests/test_model_call_reliability.py`；`tests/test_p02_review_contract.py` 的诊断字段集合补上 `call_telemetry`。
- 接口：无 REST / MCP 接口变更，无数据库迁移。节点载荷多出 `call_telemetry` 与 `call_error` 两个键。
- 兼容性：默认重试 1 次，行为差异是「超时后多试一次」；最坏耗时因此翻倍。推理强度默认不发送，请求 JSON 与现状一致。
- 不在范围：流式请求（把超时变成空闲超时）；换模型；降推理强度的效果实测（需维护者授权）；客户端断开后上游是否停止生成。
