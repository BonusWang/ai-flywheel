## Context

仓库已迭代到 v0.3.0，行为契约分散在代码、测试与 CHANGELOG 里。现在采用 OpenSpec 作为开发流程，本变更是首轮：建立项目上下文与首批基线规格。后端约 1.1 万行 Python 加 React 前端，一次性为全部能力补基线成本高，也容易写出与代码不符的纸面规格。

## Goals / Non-Goals

**Goals:**
- 让后续每个变更都能对"系统当前承诺"做 MODIFIED / ADDED 对比。
- 首批基线可核验：每条需求都能对应到现有代码或测试。
- 把本仓库的 OpenSpec 使用约定固化在 `openspec/config.yaml`，任何 AI 会话生成产物时都受同一约束。

**Non-Goals:**
- 不改任何代码或运行时行为。
- 不在本轮为全部能力补基线。
- 不引入自定义 schema 或模板，沿用 `spec-driven` 默认产物链。

## Decisions

- **首轮只建两个能力的基线：`knowledge-write-gate` 与 `workflow-orchestration`。**
  备选是全量补齐，或完全不建基线直接写修复变更。全量补齐核验成本高；完全不建会让紧随其后的修复变更无基线可比。这两个能力覆盖写入链路与运行生命周期，是下一个变更（P04 经验卡归一化修复）的直接落点。
- **基线只写现状，不夹带改进。**
  备选是顺手把已知问题写成期望行为。那会让基线失去"改之前是什么"的对照价值；已知问题留给后续变更以 MODIFIED 提出。
- **其余能力按棕地规则增量补齐。**
  触及哪个能力，就在那个变更里先补现状再写增量，避免一次性大规模文档工程。
- **能力名用 kebab-case 英文，正文用中文。**
  已安装的 openspec CLI 1.4.1 只接受 kebab-case 变更名；目录名统一用英文可避免路径与校验问题，可读性由中文标题与中文需求正文承担。
- **约定写在 `openspec/config.yaml` 的 `context` 与 `rules`。**
  该文件内容会注入每次产物生成指令，比单独的说明文档更容易被 AI 会话实际读到。

## Risks / Trade-offs

- [基线与代码不完全一致] → 每条需求在 tasks 中对照源码核验；后续 Verify 发现偏差时以代码为准修订基线，并在变更中说明。
- [未建基线的能力被直接修改] → `context` 写入棕地规则；Verify 时检查变更触及的能力是否已有基线。
- [约定是首轮拟定的，未必符合维护者习惯] → 约定集中在 `openspec/config.yaml`，调整只需改这一个文件。
