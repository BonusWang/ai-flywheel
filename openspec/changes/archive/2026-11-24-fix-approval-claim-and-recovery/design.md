## Context

现状（2026-11-24 核对代码与运行库；`orchestrator.py` 正被其他变更修改，出处按函数名定位）：

| 环节 | 现状 | 出处 |
|---|---|---|
| 取锁 | 读锁行、判过期、删除、再插入，读在写事务之外；有效期为空的行被视为永不过期；唯一调用点是启动运行 | `FlywheelDB.acquire_workflow_lock`、`start_run` |
| 批准 | 读运行、判状态、整行保存（读与写不在同一事务）→ 提问卡 `decided` → 同步执行 P04–P07；全程不取锁 | `approve_and_resume`、`_execute_post_approval` |
| 终态 | P07 现有顺序是先释锁、后保存；`_fail_run` 是读改写，不碰提问卡 | `_execute_post_approval`、`_fail_run` |
| 保存 | `save_workflow_run` 是不带状态条件的整行覆盖，任何持有旧副本的写方都会覆盖库内状态 | `FlywheelDB.save_workflow_run` |
| 恢复 | 进程重启后没有恢复逻辑 | `create_app` 的 lifespan |

约束：

- 运行库被 `serve`、`mcp-stdio`、CLI 多进程共享：每次调用各开连接、各自成事务（默认隔离级别下 SELECT 不开启事务，第一条 DML 才隐式开始）。
- 一个运行可能由 `serve` 执行，也可能由命令行进程执行；收尾不能误伤后者。
- 同一工作区另有四个进行中的变更在改 `core/orchestrator.py` 的 P02、P03、P04。

## Goals / Non-Goals

**Goals:**

- 门户与将来的飞书入口批准同一个运行，只有一方生效；批准与取消同时发生，只有一方生效。
- 持锁运行从取锁到终态的全程里，其他运行一律不能启动，不论它挂起过多久。
- 执行被中断的运行会被收尾，会话回到队列，提问卡如实反映结果。
- 提问卡状态永远与运行终态一致，且每次变化版本加一。

**Non-Goals:**

- 挂起期间释放锁。
- 批准时复核计划里的查重结果。
- 被收尾的运行已落盘写入的回滚。
- 飞书通道的发送与回写（见 `feat-feishu-approval-card-loop`）。

## Decisions

### D1. 认领原语契约：批准、取消与终态共用一个事务形状

认领原语的契约（门户与飞书两个调用方共用）：

- 入参：运行编号、被批准的项、所选选项、来源渠道（`portal` 或 `feishu`）。
- 结果三选一：已认领；锁被占用（带锁的到期时间）；运行已不在等待审批。
- 事务内写入：锁行（含新鲜的心跳时间）、运行状态、被批准的项、提问卡状态与所选选项（版本加一）、审计事件。

事务机制（本机 Python 3.11.9 与 SQLite 3.45.1 下核实过的约束）：

- 全部 SQL 内联在同一连接上；事务的第一条语句是锁行的条件 upsert 或显式 `BEGIN IMMEDIATE`；不得调用任何自开连接的现有辅助方法（第二个连接的写会等外层事务的写锁直到超时）。
- 取锁是一条带条件的 upsert（见 D2），用行数判定成败；"锁是否重新取得"在同事务内先读锁行归属再 upsert（upsert 会覆盖归属）。
- 任一步失败：整个事务回滚，运行、锁与提问卡保持原状。
- 提交之后必须重新读取运行再继续——认领事务写入的状态是唯一事实；沿用事务前读到的对象去整行保存会把状态写回等待审批。
- `save_workflow_run` 增加状态守卫：库内已是终态而传入的不是同一终态时拒绝写入。

取消走同一原语、同一事务：运行置 `PARTIAL`、准入会话恢复为 `pending`（按 `run_sessions` 关联）、P04–P07 置为跳过、写入 `lock_released`、`finished_at` 与原因、按运行编号删除锁行、关闭提问卡、追加审计事件。取消不需要取得锁，也不删除其他运行的锁行。结果摘要等展示性字段在事务之后由重新读取的运行对象补写，重复执行是幂等的。

运行进入终态只有一个入口，`_fail_run`、取消、P07 结束都调用它，形状与认领事务一致：一条带条件的更新（`WHERE status IN ('RUNNING','AWAITING_APPROVAL')`，影响 1 行才继续）先写终态，同一事务内写提问卡状态与结果摘要、审计事件并删除本运行的锁行——先写终态、后释锁，顺序与基线一致。

- 备选一：先认领再取锁，分两个事务。认领成功而取锁失败要补偿写回；两步之间崩溃留下"运行中、不持锁、提问卡仍待决"的运行。
- 备选二：提问卡状态与运行状态各认领各的。门户批准与飞书取消互不互斥，会各赢一次。
- 备选三：终态继续走读改写加整行保存。任何持有旧副本的写方都能覆盖终态，已完成的运行会被误收尾。
- 取舍：锁被占用时批准被拒绝（门户 409 并带锁的到期时间），需要稍后重试。

### D2. 取锁只有一个实现

条件以 D1 的契约为准：锁空闲、已过期、有效期为空，或属于本运行（刷新有效期与心跳）时成功。启动运行与认领共用；upsert 同时写入心跳时间，避免头 15 秒心跳为空。启动运行的取锁失败仍抛 `WorkflowLockError`，不创建运行记录、不写审计。有效期为空的旧行在迁移时删除。

- 备选：保留两套取锁。口径分裂：认领把空有效期当作可取，启动运行当作永不过期。
- 取舍：改动了启动运行的取锁路径，这条路径今天工作正常；用例覆盖"过期锁上批准与启动同时到达"。

### D3. 执行心跳与同步续期

心跳覆盖从取锁（或认领）到运行终态的全程，不只覆盖批准之后。心跳线程是守护线程：取锁或认领提交后启动，挂起分支返回前、终态入口释锁前停止并等待它结束——挂起期间不续期，锁在挂起超过有效期后可被接管。

- 后台线程每 15 秒续期一次（锁行条件更新，判行数）；续期抛出的异常只记日志、下一拍重试，线程不退出；最后一次成功续期超过 60 秒视为丢失。
- 执行线程在每个副作用之前做同步续期检查：P04 每写入一项之前、P05 每个会话结算之前、P07 交付之前各一条带条件的续期更新，以行数为准；行数为 0 且不是自己刚释放的锁时，按 fail-run 契约结束运行并注明执行期间失去独占锁。终态序列内不再检查。自己释锁后的续期影响 0 行不算丢失。
- 每个节点结束时再刷新一次（现有 `_finish_node` 处）。

- 备选一：只看锁的有效期。执行中途崩溃后最长一小时才发现，而这恰恰是最常见的重启窗口。
- 备选二：后台线程置标志、执行线程读标志。标志是异步的，睡眠醒来的执行者最长还能再写 15 秒，期间锁已释放。
- 备选三：只覆盖批准之后。P02、P03 的单次模型调用可以超过 5 分钟，健康运行会被收尾误判。

### D4. 收尾没有执行者的运行

判定条件只有一条：状态为运行中，且心跳为空或已停止刷新超过 5 分钟（心跳为空的旧行视为过期）。锁是否缺失不作单独判定——终态入口先写终态后删锁行，"运行中而锁缺失"的窗口只存在于锁被别的运行夺走之后的十几秒内，执行线程自己的同步续期会立即发现。

收尾是独立入口，不直接复用 `_fail_run`：节点时长取 `started_at` 与当前时间之差；八个节点全部完成时直接置失败并在审计注明没有失败节点；收尾本身走终态入口的条件更新，影响 0 行即跳过（收尾线程、僵尸执行者或第二个进程对同一运行只会有一个成功）。被收尾的运行若执行者其实还活着，它只允许把运行从运行中推向失败，不得再改会话状态。收尾查询按状态全量扫描，不看最近条数；循环线程逐轮捕获异常并记录，第一次收尾在循环线程里执行，不阻塞启动。

`serve` 启动时及之后每 30 秒执行一次，且只在进程角色为 `serve` 时启动。执行到 P04 中途的 `serve` 被硬杀（Ctrl+C 不会中断在工作线程里跑完 P04–P07 的批准请求）后重启，要等心跳停满 5 分钟才收尾；15 秒、30 秒、5 分钟做成可注入的模块常量，沙箱验证里缩短，不进配置文件。

- 备选一：只在启动时做。运行期间的崩溃要等到下一次重启才被发现。
- 备选二：不处理。提问卡永远显示执行中，这批会话永远停在 `in_progress`。
- 备选三：把"锁缺失"也单独算执行者消失。P07 的保存与释锁之间、锁被夺走与执行者自检之间的短暂窗口都会被误收尾。
- 取舍：崩溃后最长 5 分钟才被发现，这段时间该运行仍占着锁，新运行与批准被拒；被收尾的运行已落盘的写入不回滚，与今天任何一次 P04 中途失败相同。

### D5. 提问卡状态由运行终态推导

提问卡每次状态或所选选项变化都使版本加一——终态入口、认领事务与对账共用同一个写入函数。运行状态与提问卡状态的完整对账矩阵（无提问卡的运行一律不动，不为它凭空造卡）：

| 运行状态 | 提问卡状态 | 对账动作 |
|---|---|---|
| 运行中 | 任意 | 不动 |
| 等待审批 | 待决 | 不动 |
| 等待审批 | 非待决 | 校正回待决，清空已决定时间与所选选项，版本加一 |
| `PASS` | 已完成 | 不动 |
| `PARTIAL` | 已关闭 | 不动 |
| `FAILED` | 执行失败 | 不动 |
| 已终态 | 与终态不符 | 校正为对应终态并写入结果摘要，版本加一 |

每条校正是一条语句内同时核对运行状态的带条件更新（`EXISTS` 子查询），消除先读运行、再读卡片之间的读偏斜。对账与 D4 的检查放在同一个每 30 秒的循环里。提问卡增加结果摘要与失败节点两列，状态增加 `failed`。

- 备选：只给 `_fail_run` 补一次提问卡写入。下一条新路径还会漏，库里那张停在 `decided` 的旧卡片也不会被修好。
- 取舍：对账会改动旧卡片的状态；矩阵逐格有用例。

### D6. 统一时间源与验证

统一时钟对象经 `FlywheelRuntime`、`FlywheelDB` 与编排器的构造函数注入；取锁、续期、认领、收尾函数接受时间参数；心跳与收尾间隔做成可注入属性。

- test：并发用例分两种——对认领原语直接做多线程并发（屏障对齐起点，断言恰一方成功；桩内等待带超时，因为正确结果是一方不到达），以及执行器桩在 P04 写入处设屏障；新增测试文件自带夹具，不动现有测试文件的既有断言。
- real：独立数据目录加内置知识落点起一个沙箱 `serve`（外部动作全部关闭），缩短心跳与收尾常量；走完批准、取消两条路径，并用环境变量指定的驻留钩子（等待一个文件出现）把运行停在 P04 中途，硬杀进程后重启，确认运行被收尾、会话回到 `pending`、提问卡为执行失败；不经 REST 与界面的场景另经 REST 复核 409。

- 备选：只有 test 级证据。本变更改的是写入链路的控制流，仓库约定这类改动要有 real 级证据。

## Risks / Trade-offs

- [收尾误伤仍在执行的运行] → 判定只看心跳，执行中的运行每 15 秒刷新、每个副作用前同步续期；其它进程执行的运行同样刷心跳。
- [机器睡眠超过 5 分钟后被误收尾] → 醒来的执行者在下一次同步续期时发现锁易主，自行按 fail-run 结束，不得再改会话状态；与收尾结果一致。
- [被收尾的运行已落盘一部分写入] → 不回滚，与今天 P04 中途失败的行为相同；审计事件列出各节点状态。
- [锁被占用时批准被拒绝] → 门户返回 409 并带锁的到期时间，可稍后重试；取消不受影响。
- [启动运行的取锁路径被改动] → 用例覆盖过期锁上的竞争与"锁被占 → `WorkflowLockError`、不创建运行记录"；沙箱里走一遍完整的启动、挂起、批准。
- [与另外四个进行中的变更同改 `orchestrator.py`] → 本变更在编排器里只留委托调用，逻辑放在 `storage/db.py` 与新模块；实施前确认对方的改动已提交或已冻结。
