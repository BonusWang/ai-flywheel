## 3. 三个方案的取舍

| 维度 | A 现有全文放进提示词，模型输出完整文件 | B 更新改为追加一个小节 | C 保持整文件替换，审批并排显示新旧 |
|---|---|---|---|
| 不丢内容的保证 | 弱。靠模型遵从。可以加"原有二级小节标题必须都还在"的校验，但查不出正文被缩写或改写 | 强。由构造保证：现有文件的全部字节是新文件的开头，写入器断言这一点并回读校验 | 无。只是让丢失可见；`auto` 模式下没有人看 |
| 触发描述（frontmatter） | 由模型改写 | 原样保留 | 由模型改写 |
| P03 耗时 | 可见输出多 5–6.4 千 tokens，多 20–60 秒；叠在最慢一批的 178 秒上约 200–238 秒，贴着 240 秒超时，推理增量另计（real + static 外推，2.3） | 可见输出与现在相当（模型现在给更新项写的就是约 0.4 千字符）；输入不增，推理量预期不变（static）。实测需要一次真实模型调用 | 不变 |
| 模型上下文 | 提示词从 10.1 千字符涨到约 26 千字符（本批），输入多约 6.9 千 tokens。只能给 P02 命中的那几个；最大的 Skill 单个就有 31.4 千字符 | 不增。若同时给现有小节标题，加约 0.5 千字符（约 0.2 千 tokens） | 不变 |
| 输出被截断 | 风险高。超过 8000 字符的截断修不回来，整批失败 | 不增加 | 不变 |
| 审批界面改动量 | 可以不动。但要让一个人审得动一份重写的 270 行文件，仍需要并排差异，而且比现在更难审 | 小。卡片加「现有 N 行全部保留 · 追加 M 行」、现有小节标题、新增小节正文；「对照现有全文」需要 1 个只读接口和 1 个面板，前端约 40–120 行 | 大。1 个只读接口加逐行差异视图，前端约 200–250 行；后端不改写入 |
| 能做 | 原地修订、删除过时步骤 | 只增不改 | 同现状 |
| 拦不住的 | 没有超时余量，最大的 Skill 会超时；模型静默缩写正文时拦不住 | 不能原地修订或删除；模型看不到正文，可能追加重复小节 | 根因没动，损失靠人拦 |

各方案的一句话判断：

- **A** 把"保留原有内容"交给模型。它换来的唯一能力是原地修订；可一旦加上"原有内容必须都在"的确定性校验，原地修订就不被允许，A 就退化成成本和风险都更高的 B。耗时上没有余量，最大的 Skill 会超时。
- **B** 把"保留"从模型的任务里拿走，变成写入器的构造性质。模型只负责写增量，输出与耗时都不增。代价是不能原地修订。
- **C** 不改根因。它把损失从「看不见」变成「看得见」，但每一批都要靠人读完并手工挽救；`auto` 模式下等于没做。

## 4. 推荐做法：B 加 C 的界面部分

```
模型输出（update）                         写入器（P04，确定性，不经模型）
────────────────────────           ───────────────────────────────────────────────
## 治理缺口分层审计        ────▶    读取现有文件（不改）
1. …                                       剥掉模型可能多写的 frontmatter 与一级标题
2. …                                       追加：按原文件的行尾，空一行后接上小节
                                           断言：新内容以现有文件的全部字节开头，否则不写
                                           备份 → 临时文件 → 原子替换 → 回读比对

现有 270 行          ─────────────▶   现有 270 行（逐字节不变）+ 追加 13 行 = 283 行
```

审批卡（`smart` / `always` 模式）：

```
┌ 优化 Skill  甲                                              ┌ 现有文件 ─────────────────┐
│ 需确认原因：…；在现有文件末尾追加 1 个小节，原有 270 行不动        │ 270 行 · 9 个小节           │
│ 甲/SKILL.md                                                   │ ## 权威与适用范围           │
│ 摘要                                                          │ ## 强制执行链               │
│ ┌ 新增小节（追加到文件末尾）──────────────────┐                │ ## …                       │
│ │ ## 治理缺口分层审计（2026-11-24 补充）          │                │ （可展开全文）              │
│ │ 1. …                                      │                └───────────────────────────┘
│ └──────────────────────────────────────────┘
│ 追加后 283 行（+13）
```

配套的四道护栏，都在 P03 归一化或写入器里，不靠模型：

| 护栏 | 位置 | 处置 |
|---|---|---|
| 现有文件不是合规的 `SKILL.md`（缺 frontmatter 必填项、目录名不合规） | P03 | 丢弃留痕，原因码 `UPDATE_TARGET_INVALID` |
| 新增小节的每一行都已经在现有文件里 | P03 | 丢弃留痕，原因码 `UPDATE_NO_NEW_CONTENT` |
| 计划之后目标文件被删 | P04 | 报错，不另起新文件（小节不是一份完整的 `SKILL.md`） |
| 模型仍按旧习惯输出整份文件 | P03 归一化 | 剥掉 frontmatter 与一级标题；没有二级标题的正文包进一个小节 |

## 5. 需要维护者决定

### 5.1 主方案

| 选项 | 行为 | 代价 / 风险 |
|---|---|---|
| **B 加 C 的界面部分（推荐）** | 更新 = 追加小节；审批卡并排对照现有内容与新增小节，显示行数变化 | 不能原地修订；`auto` 模式下小节质量仍无人审 |
| B，不动界面 | 同上，审批卡只多一行「现有 N 行全部保留 · 追加 M 行」 | 审批人看不到现有小节，重复追加只能靠人凭记忆判断 |
| A 模型重写全文 | 给模型现有全文，输出保留原内容的完整文件 | 最慢一批约 200–238 秒，贴着超时且推理增量另计；最大的 Skill 会超时；截断即整批失败；原有内容是否保留靠模型 |
| C 只做审批对照 | 写入不变，审批并排显示新旧内容 | 根因未动；损失靠人拦；`auto` 模式无效 |
| D 暂停写入更新项 | `update` 项只留痕不写入，等人工处理 | 零风险，但 Skill 优化没有闭环；可作为过渡 |

### 5.2 模型写更新项时，看得到现有 Skill 的什么

| 选项 | 提示词增量（本批） | 好处 | 代价 |
|---|---|---|---|
| 仅名单（现状） | 0 | — | 模型不知道已经有哪些小节 |
| **现有小节标题清单（推荐）** | 约 0.5 千字符（约 0.2 千 tokens） | 模型知道已经覆盖了什么，提示词可以要求"只写还没覆盖的" | P03 多读几个现有文件；模型是否照做待验证；推理增量待实测 |
| 现有全文 | 约 15.9 千字符（约 6.9 千 tokens） | 模型能对着正文写 | 最大的 Skill 单个 31.4 千字符。推理增量 unknown，而耗时主要随推理走（2.3），最慢一批只剩约 60 秒余量 |

### 5.3 是否授权一次真实模型调用

| 选项 | 能证明什么 | 代价 |
|---|---|---|
| 只用桩（不授权时的默认） | 归一化、合并、审批、回读的链路（test 与沙箱回放） | 模型对新输出契约的遵从度、P03 的实测耗时保持 unknown |
| **授权一次（推荐）** | 另加：模型是否只写小节、小节质量、推理与可见 tokens 及耗时（小节标题清单带来多少推理增量） | 把那一批 P02 审查结果（含会话摘要）与现有 Skill 名、小节标题发给模型网关，消耗一次调用；写入只落沙箱副本，不碰真实技能目录 |

## 6. 设计者自行决定的点（可否决）

| 决定 | 理由 |
|---|---|
| 小节标题带日期：`## <标题>（YYYY-MM-DD 补充）` | 一眼看出哪些内容是后来追加的 |
| 不在 `SKILL.md` 里写来源脚注 | 来源进写入回执与技能资产台账；Skill 正文是给 Agent 读的，不加噪音 |
| 不动 frontmatter（含 `description`、`version`、`updated`） | frontmatter 一改写就不是"原有字节不变"。描述扩展另立项 |
| 追加在文件末尾，不判断该插在哪一节之前 | 判断插入位置只能靠启发式，会引入放错位置的风险 |
| 保留写前备份 | 追加本身不丢内容，备份是多一层保险，成本低 |
| 更新项的预览是模型写的小节，现有全文由门户按需读取 | 不把现有文件复制进运行记录、事件流与回执 |
| `create` 的行为不变 | 新建没有"原有内容"可丢 |
| 规格新建 `skill-write-gate` 能力，先补现状基线再写增量 | Skill 写入目前没有基线规格（棕地规则） |

| `auto` 模式下 Skill 更新无人审 | 换方案后不再丢内容，但追加小节的质量仍无人把关。是否让 Skill 更新在 `auto` 模式下也挂起，属于审批门规则，另立项 |
| 追加的小节可能与现有内容冲突（例如重述了适用范围） | 提示词要求只写现有 Skill 没覆盖的内容；审批卡并排对照；冲突判定不做自动化 |
| 原地修订与删除 | 本变更不提供。需要时人工修订，或另立带新旧对照的修订动作 |
| 模型调用的超时余量 | P03 最慢一批 178 秒，对 240 秒超时只剩约 60 秒；当天 15:19 真实运行的 P02 用了 197 秒，16:31 那次 P02 的第一次模型调用在 241 秒读超时，整轮失败（real，运行库）。属于 `fix-model-call-timeout-margin` 的范围。本变更不给 P02 加输入，给 P03 最多加约 0.2 千 tokens。那个变更如果降低推理强度，方案 A 的耗时要重新评估；第 3 节不选 A 的理由是原有内容是否保留只能靠模型，不随耗时改变 |
| 技能目录里此前留下的空壳 Skill | 不在本变更范围，见上一个变更的交接说明 |
