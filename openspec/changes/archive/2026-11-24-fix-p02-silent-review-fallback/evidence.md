## 7. 修复后需要知情的一点

API / CLI 模式多了一种失败：回复不是 JSON 对象、没有 `findings` 列表，或送审了会话却没有发现时，P02 失败，整轮不沉淀。两种情况的处理办法不同：

| 回复 | 是否进缓存 | 同批次重跑 |
|---|---|---|
| 不是 JSON 对象、空回复 | 不进缓存 | 重新问模型 |
| JSON 对象但缺 `findings`，或 `findings` 为空 | 进缓存 | 复用同一份回复，再次失败；删除失败信息里点名的 `p02_review-*.json` 才能让模型重答 |

两条路都可以改切 `runner.mode` 到 `dry_run`。失败信息里写明了缓存文件名与处理办法。

写用例时，API / CLI 模式下跑编排器的桩模型 P02 回复必须至少一条 `findings`（准入会话数大于 0 时）。

## 9. 真实运行（2026-11-24 #3，`run-4483f1fe5e`）

维护者授权后执行：先重启服务，再按门户「立即跑一轮」的方式触发一次。

| 步骤 | 结果 | 分级 |
|---|---|---|
| 重启前 | 默认测试 116 passed；backend 在测试期间与重启后都没有变化；无运行锁 | real |
| 重启 | 16:30:08 停掉 `serve` 进程链（不动各客户端的 `mcp-stdio`），同一命令分离启动；16:30:14 `/health` 正常。此后 backend 里晚于上一次服务启动的文件只有本变更改过的两个 | real |
| 触发 | 16:31:35 `POST /api/site/runs`（`phase=auto`，审批模式取配置 `smart`），与门户按钮相同 | real |

运行结果：**FAILED，失败节点 P02，错误 `timed out`**。

| 项 | 事实 |
|---|---|
| 准入 | 8 个会话 |
| P02 | `FAILED`，耗时 241,694 ms（API 超时阈值 240 秒）；节点载荷为空 |
| 其余节点 | P03–P07 `SKIPPED` |
| 审计 | `run_started → triage_skipped → run_failed`，没有 `review_unavailable` |
| 会话与锁 | 8 个会话全部回到 `pending`；锁已释放 |
| 写入 | 知识库 0 个文件变化；技能目录 0 增 0 改；错题观察池没有被这一轮触碰 |
| 服务日志 | 重启后的两份日志里没有 WARNING / ERROR / Traceback 行 |

怎么读这一轮：

- **失败发生在第一次模型调用上。** 模型在 240 秒内没有返回，`httpx` 抛读超时，异常原样穿出执行器，编排器按 fail-run 失败。这条路径本变更没有动：沙箱里让第一次调用抛读超时，修复前后都是「节点执行失败：timed out」、载荷为空、会话回 `pending`、零写入（见第 3 节末行），与这一轮真实记录的形状一致。它不是「审查不可用」，所以没有 `review_unavailable` 事件与诊断。
- **没有兜底、没有写入。** 与修复的方向一致，但这一轮没有走到任何新代码：审查结果还没产生，节点上就没有来源标注可供核对。
- **审查可用的路径仍未在真实模型上验证。** 任务 3.3 因此不勾选。此前真实数据里 P02 单次耗时 67–197 秒，这一次超过 240 秒；超时风险由 `fix-model-call-timeout-margin` 处理。该变更的会话从网关请求日志核实（本变更没有复核）：这次请求在 240.1 秒被客户端断开（状态 499），不是网关或上游故障；当段解码中位约 112 tokens/秒，240 秒只够生成约 2.6 万 tokens，而迄今完成的 P02 最大一次是 2.49 万。同一批次原样重跑可能再次超时，这是推断。把本地配置的 API 超时调大后重跑可以验证本变更，但那是维护者的本地配置，由维护者决定。
| 成功路径的审查来源只有节点与日志，没有审计事件 | 按设计如此：`run_started` 已记录配置的执行器，每轮多一条事件只增噪音。需要时可以补 | static |
