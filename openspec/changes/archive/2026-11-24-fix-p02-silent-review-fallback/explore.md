三点说明：

1. 兜底场景的 3 个会话全部被结算为 `processed`，沙箱知识库新增 1 篇以启发式审查结论为输入的笔记。
2. 「入池错题 2 条」在池里是 1 条：启发式审查的根因键把中文标题滤掉后只剩项目名，两个会话的模板错题合并成一条，出现次数变成 2，等级升为 `red_silent`，首次即可晋升。
3. 模板观察的 `truth` 是一句固定话术（「需核对前置条件并用真实命令验证」），`thinking_root_cause` 也是。它进的是 API 模式的运行。

### 2.4 根因链（static）

```
模型 / CLI 回复 ──▶ _invoke_api / _invoke_cli
  ├─ 不是 JSON 对象（API 先做一次仅修语法的重试） ──▶ parsed = None
  └─ 是 JSON 对象，但没有 findings 列表
        │
        ▼
review_sessions ──▶ self.fallback.review_sessions(...)   ← DryRunHeuristicRunner
  ├─ 没有日志、没有审计事件；节点摘要与 4 项内部检查全是 PASS
  ├─ 只在结果里写 runner = api_fallback_dry_run:<model> / cli_fallback_dry_run:<cmd>
  └─ 启发式审查的 findings / mistakes 原样进入后续节点：错题入池、P03 以它为输入
```

兜底从引入 API 执行器的那次提交（`79ee0ac`）起就在。三层缺口：

1. 执行器把「配置的审查器不可用」接到了另一个审查器上；
2. 接过去之后不留痕；
3. P02 对模型输出不做可用性判断：`findings` 是列表就算通过，空列表也算。

| 事实 | 影响 | 分级 |
|---|---|---|
| P02 提示词只送前 6 个准入会话，每段正文取前 3000 字符；准入上限是 10 | 第 7 个起的会话没有审查发现，运行通过后被结算为 `processed`，没有留痕。7 次 API 运行共准入 63 个会话位，19 个没有送审；两次通过的运行各有 4 个和 3 个，现在是 `processed` | static + real（只读运行库） |

| 模型返回空 `findings`（或回复是 JSON 数组被切出空列表）时照常通过 | 会话未经审查即被结算为 `processed` | real（沙箱回放） |

## 3. 需要维护者决定的问题

> **维护者的决定（2026-11-24）**：3.1 选 **A 节点失败**；3.2 选 **A 视为审查不可用**。第 4 节的设计点未否决。

### 3.1 模型审查结果不可用时怎么办

前提：`api` / `cli` 模式下，回复在格式修复之后仍不是 JSON 对象，或是 JSON 对象但没有 `findings` 列表。

| 选项 | 行为 | 写入 | 可见性 | 代价 |
|---|---|---|---|---|
| **A 节点失败（推荐）** | P02 判 `FAILED`，P03–P07 `SKIPPED`，准入会话退回 `pending`，释放锁，发失败告警；原因码与缓存文件名写进节点载荷、审计事件、日志 | 零写入，错题池不动 | 最高：失败告警 + `review_unavailable` 审计事件 + 节点摘要写明原因 | 该批当天不沉淀；回复不是 JSON 时重跑会重新问模型，没有 `findings` 列表时重跑复用缓存，需删除缓存或切 `dry_run` |
| B 显式标注降级 | 改用启发式审查继续跑，P02 摘要、载荷、审计、日志标注降级，审批规则不变 | `smart` / `auto` 模式下，以启发式审查为输入的计划直接写入 | 中：标在节点摘要里，容易略过 | 模板错题在 P02 入池，审批门拦不住；写进去的不是配置想要的审查 |
| C 挂起审批 | 改用启发式审查并强制挂起，批准才写 | 仅在人工批准后 | 高：待审批卡 + 降级原因 | 模板错题在挂起之前已经入池；`auto` 模式也会挂起并持锁等待 |

推荐 A 的理由：与 P03 的决定一致，`api` 模式的含义就是"用模型的审查"。P02 与 P03 有一点不同：P02 在审批门之前就落库，所以 B 和 C 都拦不住模板错题入池，只有失败能做到零写入。需要启发式审查时把 `runner.mode` 切到 `dry_run`，是显式的选择。

### 3.2 送审了会话，模型却没有给出任何一条发现

前提：`findings` 是列表但是空的，而提示词里有会话。提示词要求每个会话一条发现，不值得沉淀的写 `worthy=false`；空列表意味着没有任何一个会话被审查。

| 选项 | 行为 | 后果 |
|---|---|---|
| **A 视为审查不可用（推荐）** | 与 3.1 选定的处置相同（选 A 则 P02 失败），原因码记为 `EMPTY_FINDINGS` | 会话留在 `pending`，问题可见。这份回复会进缓存，重跑复用，需删除缓存或切 `dry_run` |
| B 尊重模型判断，照常继续 | 现状 | 会话被结算为 `processed`，没有沉淀也没有留痕 |
| C 继续但留痕 | P02 通过，摘要、载荷、审计、日志记下「0 条发现」 | 留痕了，会话仍然被结算 |

推荐 A 的理由：P03 把空计划当作"无可写入项"，因为写计划可以为空；对 N 个会话的审查不能为空，否则 P05 会把这些会话当作已处理。没有送审会话（准入为 0）时空列表是正常的，不在此列。

## 4. 设计者自行决定的点（可否决）

| 决定 | 理由 |
|---|---|
| 不新增方法：审查来源写进返回的字典，不可用用异常报告 | P02 的返回值本来就是字典。编排器继续调用 `review_sessions`，既有调用方和测试里的桩执行器不受影响 |
| 不可用原因分四类：空回复、无法解析、缺 `findings` 列表、没有发现；记下回复长度与是否做过格式修复 | 回复不保存，事后至少要能判断是空回复、无法解析还是缺字段 |
| 无法解析的回复再记下解码器的报错与出错位置 | 2026-11-23 #9 的回复是完整的却没有 JSON 对象，只看长度判断不了。解码器的报错只含错误类型和位置，不含回复内容 |
| 格式修复的调用自己抛异常时，记下异常类型 | 原有的 `except Exception` 会把修复调用的超时吞成"没有解析结果"。只记类型不记原文，原文带网关地址（由 `fix-model-call-timeout-margin` 的会话在核对时指出） |
| 解析失败的缓存不主动失效，失败信息指出缓存文件 | 与 P03 一致：同提示词大概率同回复，白耗一次调用 |
| 不保存解析失败的原始回复 | 与 P03 一致，不把会话内容扩散到更多存储；列为后续 |
| `dry_run` 模式只在节点上写明审查来源，行为不变 | 启发式审查是这个模式的配置选择 |
| 失败路径不新增状态，沿用 fail-run 契约 | 与 P03 一致 |
