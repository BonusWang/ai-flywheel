## Why

P02 在 `api` / `cli` 模式下，模型审查结果不可用时改用本地启发式审查，节点仍显示通过。运行记录上唯一的痕迹是节点载荷里的一个 `runner` 标签。

- **现象**：2026-11-23 #9 那次运行，8 个会话的审查实际来自启发式审查器，运行记录标 `api`，P02 为 `PASS`，审计里只有启动、挂起审批、取消三条事件。按工作区代码做沙箱回放：兜底时 P02 的摘要与一次正常的模型审查、一次 `dry_run` 运行是同一句式；P03 摘要写「计划来源：API 模型」，而计划的输入是启发式审查的结论。
- **影响**：维护者以为看到的是模型的审查。启发式审查的错题是固定话术，在 P02 直接入错题观察池，审批门拦不住，取消放行也撤不掉。日志 0 条，审计 0 条。
- **根因分三层**，缺一不可：
  1. 执行器在模型输出不可用时接到了另一个审查器上（自引入 API 执行器的提交 `79ee0ac` 起）；
  2. 接过去不留痕：没有日志、审计事件与节点标记；
  3. P02 对审查结果不做可用性判断：`findings` 是列表就算通过，空列表也算，会话未经审查即被结算为 `processed`。

证据见 [explore.md](./explore.md)：只读运行库（real）、缓存输出离线回放（real）、沙箱回放（real）、代码与 git 历史（static）。

## What Changes

- **BREAKING**：`api` / `cli` 模式下不再兜底。模型回复无法解析、没有 `findings` 列表，或送审了会话却没有任何发现时，P02 失败（fail-run 契约），不再改用启发式审查；错题观察池与分歧记录不变。
- **审查不可用留痕**：原因码、回复长度、解码器拒绝的原因、是否做过格式修复、缓存文件写进日志、P02 节点摘要与载荷、`review_unavailable` 审计事件。失败信息指出缓存文件与处理办法。
- **审查来源写进节点**：P02 摘要与载荷写明审查来自模型、本地 CLI 还是本地启发式审查器。
- 回归测试覆盖「无法解析时失败」「空发现时失败」「留痕齐全」「来源标注」「CLI 同契约」。

## Capabilities

### New Capabilities
- `session-review-contract`: 会话审查契约。P02 执行器的提示词与输出契约、输出缓存与格式修复、审查来源、审查不可用的判定与诊断。前两条要求是现状基线，其余为本次增量。

### Modified Capabilities
- `workflow-orchestration`: P02 全文审查与错题入池。节点需写明审查来源；执行器报告审查不可用时按 fail-run 契约失败并留痕。

## Impact

- 代码：`adapters/runners.py`（三个执行器的 `review_sessions`、`ReviewUnavailableError`、`ReviewDiagnostics`、`_invoke_api` / `_invoke_cli` 的回执参数）、`core/orchestrator.py`（P02 留痕与失败）。
- 测试：新增 `tests/test_p02_review_contract.py`；`tests/test_p03_plan_contract.py` 的桩模型 P02 回复从空发现改为一条发现，否则 5 个用例会在 P02 失败。
- 兼容性：无数据库迁移、无配置项变更、无 REST / MCP 接口变更；`review_sessions` 的签名与返回类型不变。行为差异两处（见 BREAKING）；正在运行的服务重启后生效。
- 不在范围：P02 只送审前 6 个会话、每段前 3000 字符；启发式审查的模板错题入池与晋升；解析失败的原始回复不留存。
