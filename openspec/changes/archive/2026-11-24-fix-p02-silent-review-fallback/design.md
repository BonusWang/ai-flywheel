## Context

P02 的审查有两个来源：`api` / `cli` 模式下来自模型，`dry_run` 模式下来自本地启发式审查器。现状把两者悄悄接在了一起：模型回复不可用时改用启发式审查，节点照常 `PASS`，只在结果里留一个 `runner` 标签。

| 事实 | 出处 |
|---|---|
| 7 次 API 模式运行里有 1 次（2026-11-23 #9）的审查来自启发式审查器；P02 为 `PASS`，运行记录标 `api`，审计里没有任何相关事件 | explore.md 2.1（real） |
| 兜底的 P02 摘要与正常审查、`dry_run` 运行是同一句式；日志 0 条 | explore.md 2.3（real） |
| 启发式审查的模板错题在 P02 入池：挂起审批之前已经写入，取消放行后仍在 | explore.md 2.3（real） |
| 5 份缓存输出全部可解析且带 `findings`；P02 的输出契约没有漂移 | explore.md 2.2（real） |
| 回复是 JSON 数组时，花括号切片切出内层对象，空的 `findings` 被当作正常审查 | explore.md 2.2（real） |
| 在途测试里有不继承基类的桩执行器，只实现 `review_sessions` | explore.md 6（static） |

约束（`openspec/config.yaml`）：LLM 输出一律视为不可信；失败遵守 fail-run 契约；公开仓库不含个人路径与私有名称。

## Goals / Non-Goals

**Goals:**
- `api` / `cli` 模式下不再出现"标着模型、实际是启发式"的审查。
- 审查不可用时有日志、有审计事件、节点上写明原因。
- 事后能从运行记录分辨每一次 P02 的审查来自哪里。
- 审查不可用时不往错题观察池写任何东西。

**Non-Goals:**
- 不改 P02 的送审范围（前 6 个会话、每段前 3000 字符）。
- 不改启发式审查器的产出，不处理它的模板错题入池与晋升。
- 不保存解析失败的原始回复。
- 不新增配置项，不引入日志配置，不改 P03。

## Decisions

- **审查不可用时 P02 失败（维护者决定）。**
  备选「显式标注降级」：改用启发式审查继续跑，四处标注，无人值守也出结果。备选「挂起审批」：改用启发式审查并强制挂起。两者都保住了批次，但 P02 与 P03 有一点不同：P02 在审批门之前就把错题写进观察池，沙箱回放里挂起时池里已经有 1 条模板观察，取消放行后仍在。所以标注和挂起都拦不住兜底的副作用，只有失败能做到零写入。`api` 模式的含义就是"用模型的审查"；需要启发式审查时把 `runner.mode` 切到 `dry_run`，是显式的选择。失败走现有 fail-run 契约，不新增状态。

- **送审了会话却没有发现，视为审查不可用（维护者决定）。**
  备选是照 P03 的做法把空列表当作模型的明确判断。P03 的计划可以为空，因为"没有值得写的"是成立的结论；对 N 个会话的审查不能为空：提示词要求每个会话一条发现，不值得沉淀的写 `worthy=false`。空列表意味着没有任何会话被审查，而 P05 会把它们结算为 `processed`。准入为 0 时空列表是正常的，不在此列。

- **不新增执行器方法：来源写进结果，不可用用异常报告。**
  P03 加了 `plan_writes_detailed`，是因为 `plan_writes` 返回类型化列表，带不了诊断。P02 的 `review_sessions` 返回的就是字典。备选一是照 P03 加 `review_sessions_detailed`：在途测试里的桩执行器不继承基类，只实现了 `review_sessions`，加方法会让那些用例失效。备选二是编排器从 `runner` 标签字符串推断来源：那是给人看的标签，格式一变就会标错。备选三是从 `run.runner_mode` 推断：它描述的是配置的执行器，不是实际审查的那个，这恰恰是原缺陷。改为由做审查的执行器在结果里写 `review_source` 与 `review_diagnostics`；结果里没有来源时节点写「未声明」，不推断。`review_sessions` 的签名与返回类型不变。

- **不可用分四个原因码，诊断记下回复长度、是否做过格式修复，以及解码器为什么拒绝。**
  原因码：`EMPTY_REPLY`（回复为空）、`UNPARSABLE_REPLY`（不是 JSON 对象）、`FINDINGS_NOT_LIST`（没有 `findings` 列表）、`EMPTY_FINDINGS`（送审了会话却没有发现）。备选是只报"不可用"：2026-11-23 #9 就是这样一个查不出原因的失败，回复没有保存。只记回复长度也不够：网关日志表明那次回复是完整的，不是截断，长度说明不了它为什么没有 JSON 对象。所以在回复不是 JSON 对象时再记下解码器对最外层花括号的报错与出错位置（没有花括号、对象没有闭合，或具体的解码错误），格式修复后的回复同样处理。解码器的报错只有错误类型和位置，没有回复内容。格式修复的那次调用自己抛异常时（读超时、连接错误），原有的 `except Exception` 会把它吞成"没有解析结果"，诊断就会把一次超时写成"已做过一次格式修复"。所以这时改记异常类型（`repair_error`），失败信息写「格式修复的调用没有完成（ReadTimeout）」。只记类型不记原文：异常原文带网关地址。备选是把原始回复留一段：会把会话内容扩散到节点载荷、回执和审计里，与 P03「不把会话内容扩散到更多存储」相悖，列为后续。回复长度、解码报错与修复调用的异常类型由 `_invoke_api` / `_invoke_cli` 写进调用方传入的可选字典，只有 P02 传；P03 的调用不变，所以 P03 的修复调用超时仍显示为「计划不可用」。

- **失败路径留痕四处，各管一件事。**
  日志给排障时间线（编排器记一条 WARNING，带运行号）；节点摘要在失败原因里写明是哪种不可用；节点载荷存结构化诊断（来源、原因码、回复长度、缓存文件）；审计事件 `review_unavailable` 是不可变时间线，门户「操作记录」直接可见。执行器自身不记日志，避免同一事件记两条，与 P03 一致。

- **成功路径把审查来源写进节点，并记一条 INFO 日志。**
  P02 摘要以「审查来源：…；」开头，载荷带 `review_source` 与 `review_diagnostics`（送审会话数、发现条数、缓存文件与命中情况）。不为每次运行追加审计事件：`run_started` 已经记了配置的执行器，每轮多一条事件只增噪音。备选「只在载荷里放来源」被否决：摘要才是门户一眼能看到的地方。

- **缓存不主动失效，失败信息指出缓存文件。**
  与 P03 同理：同提示词在低温下大概率给出同样的回复，删缓存重问多半白耗一次调用。这里有两种情况。回复不是 JSON 对象时从来没有进缓存，重跑会重新问模型；回复是 JSON 对象但缺 `findings` 或发现为空时已经进了缓存，同批次重跑会复用，删除该文件才能让模型重答。

- **`dry_run` 模式只标注来源，行为不变。**
  启发式审查是这个模式的配置选择，节点如实写明即可。

- **验证分两级。**
  - test：pytest。用例覆盖四个原因码、无会话时的空列表、JSON 数组回复、三种截断形态的解码报错、诊断不含回复正文、失败后的节点状态与留痕、三种来源与未声明来源、CLI 同契约、缓存命中与格式修复只重试一次。
  - real：沙箱回放。真实编排器从 P00 跑到 P07，桩模型，虚构会话，知识根、数据目录、技能目录全部在一次性沙箱内，飞书、Webhook、Git 收口关闭，不联网、不调模型；修复前后各跑一遍对照。另把 5 份真实缓存输出经修复后的 API 执行器离线回放，确认可用审查不受影响。真实知识库与真实模型上的一轮运行需要维护者授权，授权前保持未验证。

## Risks / Trade-offs

- [审查不可用即失败，该批当天不沉淀] → 会话退回 `pending`、释锁、发失败告警，不丢数据；失败信息给出缓存文件名与两条处理办法（删除缓存或切 `dry_run`）。
- [回复不是 JSON 对象时，每次重跑都失败] → 诊断记下回复长度和解码器的报错，能分出空回复、被截断、完整的回复里没有 JSON 对象三种情况。2026-11-23 #9 属于第三种，回复是什么形态仍是 unknown：那份回复没有保存。
- [P02 单次调用最长约 197 秒，阈值 240 秒] → 超时抛异常，运行按 fail-run 失败并有告警，与本变更的失败路径相同；耗时本身由 `fix-model-call-timeout-margin` 处理。
- [真实服务要重启才加载新代码] → 重启之前，真实运行里的 P02 仍会静默兜底；重启后生效，没有需要迁移的状态。
- [模型调用本身抛异常（读超时、HTTP 错误）] → 异常照常抛出，运行按 fail-run 失败并有告警，但没有 `review_unavailable` 事件与结构化诊断。调用级的重试与留痕由 `fix-model-call-timeout-margin` 处理。
- [缓存里的无效回复让同批次重跑再次失败] → 这是有意的：结论稳定且可见，失败信息写明删除哪个文件。
- [新契约下，桩模型返回空 `findings` 的既有用例会在 P02 失败] → 改一处夹具（`tests/test_p03_plan_contract.py` 的桩模型 P02 回复）；在途的两个变更已被告知新契约。
- [执行器没有声明来源] → 节点写「未声明」，不会误标成模型或启发式。
- [P02 仍然只送审前 6 个会话] → 不在范围。真实数据里 7 次 API 运行有 19 个会话位没有送审，列为后续。

## Migration Plan

无配置变更、无数据库迁移、无接口变更，服务重启后生效。行为差异两处：

| 场景 | 之前 | 之后 |
|---|---|---|
| `api` / `cli` 模式下回复无法解析，或没有 `findings` 列表 | 静默改用启发式审查，P02 为 `PASS` | P02 为 `FAILED`，整轮不审查、不写入 |
| `api` / `cli` 模式下送审了会话，`findings` 却为空 | P02 为 `PASS`，会话被结算为 `processed` | P02 为 `FAILED`，会话留在 `pending` |

审查可用时节点多了一行来源标注，没有行为差异。正在运行的服务用的是启动时加载的代码，重启之后新行为才生效；没有需要迁移的状态。回滚即还原这两个文件，没有需要清理的状态。
