修正一个说法：不是"每一次 API 模式运行"都兜底。改写提示词之前的那个批次字段齐全、走的是模型计划；改写之后的 4 个批次全部兜底。

### 2.2 根因链（static）

```
v0.2 提示词改写 (cb49225)
  逐项骨架 {"target_kind","relative_path","action","title","summary","content_preview",...}
  ──▶ {"planned_writes":[...]}（字段只在各类型的散文描述里，没有 title / summary）
        │
        ▼
模型输出不带 title / summary
        │
        ▼
_normalize_planned_write：PlannedWrite 校验失败 ──▶ return None（无日志、无审计）
        │
        ▼
OpenAICompatibleRunner / CliSubprocessRunner.plan_writes：out 为空
  ──▶ return self.fallback.plan_writes(...)（无日志、无审计、无节点标记；run.runner_mode 仍是 api:<model>）
```

三层都缺防线：提示词契约、丢弃留痕、兜底留痕。只补其中一层，下一类不合规输出仍会静默通过。

### 2.3 空壳 Skill 的机制（real）

| 环节 | 事实 |
|---|---|
| P02（模型） | `repeated_workflows` 里 `action=update` 的候选，`name_hint` 是新起的名字，`existing_skill_match` 才是现有 Skill 名；最近一批 3 个候选 3 个都是这样 |
| 模型自己的 P03 | 5 个 `update` 项的目录全部是现有 Skill 目录（磁盘上存在） |
| 启发式 P03 | 取 `name_hint` 当目录，正文是固定的三步模板话术；P04 的写入器遇到目标不存在时把 `update` 静默当成新建 |

所以模型计划本身指向是对的，被丢弃后由启发式计划器改了指向。

### 2.4 修复后的预期影响（real，离线回放，真实挂载 Schema 只读校验）

| 检查 | 结果 |
|---|---|
| 补全 `summary` / `title` 后通过归一化 | 23 / 23 |
| 9 篇知识文档按 T5 归一化能否归属项目 | 3 篇可归属，6 篇无法归属（会被 P03 移出计划并留痕） |
| 缺 `source_session_keys` 的知识文档 | 6 / 9（提示词没要求；缺了它，来源会话工作区这条最强证据用不上） |
| 来源会话工作区能直接归属的会话 | 5 个批次 26 个有效发现里 3 个 |

两点需要维护者知情：

1. 修复后第一次真实运行会用**模型的计划**。在 `smart` 审批下 Skill 变更仍会挂起，但批准后模型的 SKILL.md（提示词要求 250–500 字符）会**整文件覆盖**现有 Skill（写入器留备份）。这是既有的更新语义，本变更不改，见第 5 节。
2. 模型计划里的知识文档不带 `source_session_keys` 时只能靠内容证据归属。本变更把该字段写进输出契约；新输出会带，旧缓存不会。

### 2.5 现状的其他事实（static）

| 事实 | 影响 |
|---|---|
| 后端没有任何日志调用（无 `logging`） | "日志留痕"需要引入标准库 logger；WARNING 级别经 last-resort handler 输出到 stderr |
| 门户的状态标签里 `PARTIAL` 显示为「已取消」，运行与节点共用 | 降级不能靠把节点置为 `PARTIAL` 来表达 |

## 3. 需要维护者决定的问题

> **维护者的决定（2026-11-24）**：3.1 选 **A 节点失败**；3.2 选 **S1 不再产出 Skill 写入**。第 4 节的设计点未否决。

### 3.1 模型计划项全部被丢弃时怎么办

前提：字段补全之后仍然全部无效（例如出现新的契约漂移），或模型没有返回可解析的计划。

| 选项 | 行为 | 写入 | 可见性 | 代价 |
|---|---|---|---|---|
| **A 节点失败（推荐）** | P03 判 `FAILED`，P04–P07 `SKIPPED`，准入会话退回 `pending`，释放锁，发失败告警 | 零写入 | 最高：失败告警 + 逐项丢弃原因进审计 | 该批当天不沉淀，需人工介入（修契约、删对应缓存或切 `dry_run`） |
| B 挂起审批 | 改用启发式计划（只有笔记与规则）并强制挂起，批准才写，可取消 | 仅在人工批准后 | 高：待审批卡 + 降级原因 | 新增"降级挂起"语义；`auto` 模式也会挂起并持锁等待 |
| C 显式标注降级 | 改用启发式计划继续跑，在 P03 摘要、载荷、审计、日志标注，审批规则不变 | `smart` 模式下笔记自动写入 | 中：标在节点摘要里，容易略过 | 降级内容仍会进知识库 |

推荐 A 的理由：API 模式的含义就是"用模型的计划"。模型计划不可用时换成另一个计划器，无论标注得多清楚，写进去的都不是配置想要的产物。需要启发式计划时把 `runner.mode` 切到 `dry_run`，是有审计记录的显式选择。B 能保住批次，但本质上是把"要不要切 dry_run"变成每批点一次。

### 3.2 启发式计划器还要不要产出 Skill 写入

| 选项 | 行为 | 风险 |
|---|---|---|
| **S1 不再产出（推荐）** | 只产笔记与规则；重复流程候选的数量与目标在 P03 摘要、载荷、审计事件里留痕。Skill 只来自模型计划（经审批）或人工 | 零配置演练模式不再自动封装 Skill |
| S2 产出基于会话证据的草稿 | `update` 指向现有 Skill 目录，正文取会话事实而非模板 | 用自动草稿整文件覆盖现有 SKILL.md（有备份）；演练模式下"会话事实"只是正文前 220 字符 |

只把 `update` 指向现有目录而不改正文，会让模板话术覆盖真实 Skill，比现在更糟。

## 4. 设计者自行决定的点（可否决）

| 决定 | 理由 |
|---|---|
| 模型返回空列表视为"无可写入项"，不再兜底 | 空列表是模型的明确判断，现状会把它覆盖成启发式计划 |
| 部分丢弃只留痕，不强制挂起 | 保留项本身合规；强制挂起会让每一次字段漂移都变成人工负担 |
| 输出契约加入 `source_session_keys` | 归属判定优先用来源会话工作区，模型不给这个字段就用不上 |
| Skill 项动作与目标目录状态对齐：`update` 目标不存在则丢弃留痕；`create` 目标已存在则改标为 `update` | 门户标签取自动作；写入器遇到不一致会静默改动作 |
| 诊断信息经新的 `plan_writes_detailed` 返回，`plan_writes` 仍返回列表 | 编排器需要丢弃明细才能写进节点载荷与审计；保持既有方法签名 |
