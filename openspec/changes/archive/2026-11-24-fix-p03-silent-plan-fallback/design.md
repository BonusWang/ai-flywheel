## Context

P03 的写入计划有两个来源：`api` / `cli` 模式下来自模型，`dry_run` 模式下来自本地启发式计划器。现状把两者悄悄接在了一起：模型计划项只要有一项没过 `PlannedWrite` 校验就被丢弃，全部丢弃后改用启发式计划器，三步都不留痕。

| 事实 | 出处 |
|---|---|
| 5 个缓存批次 23 项，16 项因缺 `summary`（其中 6 项还缺 `title`）被丢弃，4 个批次整批兜底 | explore.md 2.1（real） |
| 提示词改写删掉了逐项字段骨架，是缺字段的直接原因 | explore.md 2.2（static） |
| 空壳 Skill 来自启发式计划器取 `name_hint` 当目录；模型自己的 5 个 `update` 项指向的都是现有目录 | explore.md 2.3（real） |
| 后端没有任何日志调用；门户的 `PARTIAL` 标签显示为「已取消」 | explore.md 2.5（static） |
| 字段补全后 23 / 23 项可保留；模型文档不带 `source_session_keys`，6 / 9 篇无法归属项目 | explore.md 2.4（real） |

约束（`openspec/config.yaml`）：LLM 输出一律视为不可信，进入 P04 前必须经过确定性归一化与校验；失败遵守 fail-run 契约；公开仓库不含个人路径与私有名称。

## Goals / Non-Goals

**Goals:**
- 模型计划只要有一项可用，就用模型的计划；可补全的字段补全，不丢项。
- 任何一项被丢弃、任何一个候选没成计划，都在日志、P03 节点和审计里看得到。
- `api` / `cli` 模式下不再出现"标着模型、实际是启发式"的计划。
- 启发式计划器不再往技能目录写模板正文，也不再另起目录。

**Non-Goals:**
- 不改 P02 审查环节的兜底（同类缺陷，另行立项）。
- 不改 Skill 更新的整文件覆盖语义。
- 不改经验卡的项目归属判定，不处理模型耗时。
- 不新增配置项，不引入日志框架或日志配置。

## Decisions

- **三层同时设防：契约、补全、留痕。**
  备选一是只改提示词。它修掉已知的这一种漂移，但下一类不合规输出仍会被静默丢弃。备选二是只在丢弃处留痕、保留兜底。那样问题可见了，写进去的仍然不是配置想要的产物。三者各自独立成立：契约减少不合规，补全挽救可挽救的项，留痕兜住剩下的。

- **全部无效时 P03 失败（维护者决定）。**
  备选「挂起审批」：改用启发式计划并强制人工确认，能保住批次，但新增一种挂起语义，`auto` 模式也会挂起并持锁等待。备选「显式标注降级」：无人值守也出结果，但 `smart` 模式下降级笔记会自动写进知识库。选失败的理由是 `api` 模式的含义就是"用模型的计划"；需要启发式计划时把 `runner.mode` 切到 `dry_run`，是有审计记录的显式选择。失败走现有 fail-run 契约，不新增状态。

- **启发式计划器不产出 Skill 写入（维护者决定）。**
  备选一是只把 `update` 指向现有目录。那会让模板话术覆盖真实 Skill，比现在更糟。备选二是用会话事实生成草稿正文。它保留了演练模式的 Skill 闭环，但自动草稿会整文件覆盖现有 `SKILL.md`，而演练模式的"会话事实"只是正文前 220 字符。关键词触发的启发式写不出可执行的 Skill，产出本身就是 Skill 表演，所以不产出，候选只留痕。

- **补全只补 `title` 与 `summary`，来源顺序固定。**
  备选一是缺 `summary` 一律取标题。标题只有几个字，补出来的摘要信息量低，而摘要在经验卡归一化时会成为描述。所以知识文档优先取正文首句。备选二是让模型带着报错重试一次。P03 耗时已经逼近超时，多一次往返不划算；确定性补全零成本且可测。来源顺序写在规格里，诊断记录补全了哪些字段，提示词契约是否被遵守一目了然。

- **诊断随计划返回，`plan_writes` 的签名与返回类型不变。**
  编排器需要丢弃明细才能写进节点载荷与审计。备选一是让 `plan_writes` 返回结果对象，会破坏既有调用方。备选二是把诊断挂在执行器实例上，是隐式状态。改为新增 `plan_writes_detailed`，返回计划与诊断；`plan_writes` 保留为只取计划的薄封装。

- **留痕四处，各管一件事。**
  日志给排障时间线；节点摘要让门户一眼看到数量；节点载荷存结构化明细（序号、类型、动作、原因码）；审计事件是不可变时间线，门户「操作记录」直接可见。明细不含计划项正文，避免把会话内容扩散到更多存储。日志用标准库 `logging` 的模块 logger（`ai_flywheel.adapters.runners` 与 `ai_flywheel.core.orchestrator`），丢弃记 WARNING，补全与超限记 INFO；不新增日志配置，没有配置 handler 时 WARNING 经 last-resort handler 进 stderr。

- **Skill 计划项的动作必须与目标目录的实际状态一致，校验放在 P03 归一化；审批理由写明更新的写入方式。**
  校验对象是写入器实际会写的路径（主技能目录下 `<目录名>/SKILL.md`），不是 Skill 名单：名单取的是 frontmatter 的 `name`，它可能与目录名不同。`update` 目标不存在则丢弃，因为写入器会把这种 `update` 静默当成新建；`create` 目标已存在则改标为 `update`，因为写入器会备份后覆盖，门户标签应当如实。备选是在 P04 写入器里拦截，但那样一项不合规会让整批失败。
  模型的 Skill 项此前从未真正进入写入环节。沙箱回放显示它的 `update` 会把一个 270 行的现有 `SKILL.md` 换成 12 行（有备份），所以 `update` 项的审批理由必须写明"整文件替换、原文件自动备份"。覆盖语义本身不在本变更范围。

- **模型返回空列表视为无可写入项。**
  现状把空列表也当成"没有保留项"去兜底，等于用启发式计划覆盖模型的明确判断。

- **缓存不主动失效，失败信息指出缓存文件。**
  备选是计划无效时删除缓存、让模型重答。同一提示词在低温下大概率给出同样的答案，白白多一次两三分钟的调用，也破坏了"同提示词同输出"的缓存语义。改为在诊断与失败信息里给出缓存文件名和处理办法：删除该文件可让模型重答，切 `dry_run` 可显式改用启发式计划。

- **验证分两级。**
  - test：pytest。用例按真实缓存输出的形状脱敏构造（缺 `summary`；缺 `title` 与 `summary`；规则项只有载荷；Skill 项带路由与 frontmatter），覆盖部分丢弃留痕、全部丢弃不静默、不新建模板 Skill、动作与目标一致、输出契约。
  - real：沙箱回放。真实编排器 + 真实缓存输出（经真实的 API 执行器与归一化代码）+ Wiki 与技能目录的沙箱副本；知识根、数据目录、证据目录全部重定向，飞书、Webhook、Git 收口硬关闭，不联网、不调模型。真实知识库与真实技能目录上的完整运行需要维护者授权，授权前保持未验证。

## Risks / Trade-offs

- [全部无效即失败，该批当天不沉淀] → 会话退回 `pending`、释锁、发失败告警，不丢数据；失败信息给出缓存文件名与两条处理办法。
- [同一批次重跑命中同一份无效缓存，再次失败] → 这是有意的：结论稳定且可见。失败信息写明删除缓存可让模型重答。
- [演练模式不再自动封装 Skill] → 候选在 P03 摘要、载荷与审计里留痕；需要 Skill 时用 `api` / `cli` 模式经审批产出，或人工编写。
- [补全出的摘要取决于正文首句的质量] → 只补必填字段，不改写内容；补全计数进诊断，便于判断是否该收紧提示词。
- [修复后模型的 Skill 项第一次真正进入写入环节，`update` 会整文件覆盖现有 `SKILL.md`（有备份）] → 既有更新语义，本变更不改；`smart` 与 `always` 模式下 Skill 变更仍挂起审批；提示词写明更新是整文件替换，要求输出完整的 `SKILL.md`。列为后续。
- [演练模式识别到的重复流程不再有任何自动出口] → 候选连同目标 Skill 留在节点载荷与审计里，需要时由人据此编写，或改用 `api` / `cli` 模式经审批产出。
- [P03 到审批之间 Skill 被删除，P04 仍会把 `update` 当成新建] → 窗口极小；P03 已挡住所有可预见的情况。列为后续。
- [P02 审查环节仍有同类无留痕兜底] → 不在范围，列为后续。

## Migration Plan

无配置变更、无数据库迁移、无接口变更，升级即生效。两处行为差异：

| 场景 | 之前 | 之后 |
|---|---|---|
| `api` / `cli` 模式下模型计划全部无效或无法解析 | 静默改用启发式计划 | P03 失败，整轮不写入 |
| `dry_run` 模式下识别到重复流程候选 | 产出模板正文的 Skill 写入（经审批后落盘） | 不产出 Skill 写入，候选留痕 |

回滚即还原这两个文件，没有需要清理的状态。
