约束：

- 本机优先：服务只监听本机，不引入公网入口。
- 公开仓库不含个人标识；个人配置只在 `flywheel.yaml`。
- 执行器输出的标题、摘要、审批理由不可信，会进入发往飞书的文本。
- 运行库被 `serve`、`mcp-stdio`、CLI 多进程共享，每次调用各开连接、各自成事务。
- 信任边界：飞书回答者校验只对飞书侧的身份有效，不是本机的授权边界。能访问本机端口、能写 `serve` 工作目录或 npm 目录的进程，与门户同权。
- 同一工作区另有多项变更在改 `core/orchestrator.py`。

本机 lark-cli（1.0.68，npm 包装加原生 `lark-cli.exe`）的命令面：

飞书平台约束（官方文档口径，未实测）：

- 卡片回调可用长连接订阅（仅企业自建应用）；同一应用的多个客户端是集群模式，只有一个随机收到。lark-cli 对该事件标记为单消费者，第二个消费者会被拒绝。
- 回调须 3 秒内应答且不补推；长连接模式下应答方是 lark-cli。
- 按消息修改卡片：仅限 interactive、调用身份与发送者一致、14 天内、单条 5 QPS、`update_multi` 须为 `true`。
- 卡片 2.0：须显式声明 `schema`，不超过 30KB、200 个元素。
- 发送幂等键 1 小时内至多发一条，不超过 50 字符。
- 回调须在开发者后台手动订阅并发布应用版本，保存订阅时本地客户端须在线；lark-cli 不提供预检。

参照实现（agent-autoloop `1b89219`）可直接借鉴的几条：卡片内容创建后不变、只变状态，每次状态变化版本加一；回答校验顺序是身份 → 消息引用 → 是否仍待决；投递按（卡片, 通道）一行受管，按 0、1、3、7、15、25、35、45、55 分钟退避共 9 次、57 分钟放弃；首条消息的幂等键只用卡片编号；未送达就结束的提问卡不再投递。

## Goals / Non-Goals

**Goals:**

- 人不在电脑前，也能在飞书里完成批准或取消，并看到执行结果。
- 门户与飞书是同一张提问卡的两个入口：行为一致、留痕一致、只有一方生效。
- 投递失败可恢复、可见；决定与结果回到同一张卡片。
- 链路没通时能被发现，且不会出现点了没反应的按钮。

**Non-Goals:**

- 批准与取消的原子认领、锁续期、中断运行的收尾、提问卡状态与运行终态的对账（见 `fix-approval-claim-and-recovery`）。
- smart 模式拆批。
- 飞书内逐项勾选、文字回复指令；可供手机打开的回答链接；超时催办。
- 放弃后的门户重发；批准时复核计划的查重结果。
- P03 计划质量与路由归属；飞书以外的通道。

## Decisions

### D1. 复用本机 lark-cli，不直连飞书 OpenAPI

发送、修改卡片、接收点击都经本机 lark-cli：它是现成的凭据持有者，并自带事件总线长连接，本机不需要公网地址。要求版本不低于 1.0.64。

- 备选一：飞书 SDK 自建长连接。要新增应用凭据与一条常驻连接，和 lark-cli 抢同一个应用的回调。
- 备选二：Request URL 回调。要求公网地址，违背本机优先。
- 取舍：多一层对 lark-cli 的运行时依赖，命令面会随版本变化（参照实现用的 `im messages patch` 在本机就不存在）。调用层单独成模块，自检在 lark-cli 变化后必须重跑。

### D2. 点击监听只在 `flywheel serve`，且是唯一消费者

在 FastAPI 的 lifespan 里按配置启动一个常驻线程，线程内拉起 `event consume` 子进程并逐行读回调。自检经 `serve` 的接口执行，复用同一个监听器；CLI 与 `mcp-stdio` 不起监听。子进程契约按 lark-cli 内嵌文档执行：

- stdin 接管道且永不关闭；以 stderr 的 `[event] ready` 行作为就绪判据。
- stdout 与 stderr 各用一个线程排空，按字节换行切分，以 UTF-8 解码并用替换方式处理坏字节。
- 退出原因按 stderr 的错误文案判定，退出码只作粗分类。鉴权失败、版本或参数不符属永久性错误：等 60 秒重启，连续 5 次后停止并标为已停止；被别的消费者占用、网络错误属临时性错误：退避从 60 秒起、最长 5 分钟，不永久停止。连续计数在收到就绪行后清零。
- 审计只在状态切换时记（进入退避一条、恢复一条），不逐次追加。
- 每轮循环从当前配置对象重新取通道开关与交互模式：任一被关闭就停掉子进程，重新打开时再拉起。受理在监听线程内逐事件同步完成，没有"已读取未受理"的队列。
- 停止时先关闭 stdin 让它自行退出，10 秒内未退出就结束整棵进程树；子进程放进独立进程组。`uvicorn.run` 传入 10 秒的关闭宽限，否则开着的门户页面会让 lifespan 的关闭永远等不到。

- 备选：独立守护进程。多一个要管理的进程，且与 `serve` 抢同一份运行库。
- 取舍：`serve` 没运行时收不到点击。这个前提由 D5 兜住——监听不在时退回文本，由 D6 把已发出卡片的按钮收掉。

### D3. 受理在监听线程完成，执行交给唯一的执行线程

监听线程按 D7 校验后直接调用认领原语（`fix-approval-claim-and-recovery` 提供的事务），把运行交给唯一的执行线程。锁被别的运行持有时认领失败，监听线程把一个带点击时卡片版本的提示任务交给发件箱线程，随即回到读回调；提示与受理后的回写都由发件箱线程串行执行，卡片版本已变即丢弃，同一事件的重复投递按事件编号去重，提示不写入已同步的版本。监听线程不直接改卡。提示只写明另一批次正在执行、可稍后再点——锁在执行期间持续续期，锁的到期时间与实际可重试时间无关。调用层的单次调用有超时上限，监听线程在等待改卡的几秒内不读回调是可接受的。

认领需要独占锁，所以同一时刻至多有一个运行在执行，执行线程的队列深度为 1。"已认领、尚未开始执行"的运行不会被误判为无执行者：认领事务写入新鲜的心跳，执行线程一开始就接上心跳。受理后的第一次回写（处理中）由执行线程在开始 P04 之前触发、由发件箱线程优先执行，排在所有首发与重试之前。

- 备选一：监听线程只校验入队，取锁与认领都在工作线程里。工作线程忙时回答要排几分钟的队，锁忙提示也出不来，还会把一次本该被拒的点击延后成一次无人注视的批准。
- 备选二：监听线程里认领后直接执行。P04–P07 是分钟级，会堵住回调读取。
- 取舍：认领后、执行前进程崩溃，运行会被 `fix-approval-claim-and-recovery` 的收尾按中断处理，这次点击需要重来。

### D4. 投递改为发件箱，按（卡片, 通道）受管

挂起时先把提问卡和各通道的投递记录落库，再发送。交互卡片与文本通知是两行：通道名分别是 `feishu_cli` 与 `feishu_text`，各有各的幂等键。`card_deliveries` 增加 `synced_version`、`synced_avail`、`first_try_at`、`next_attempt_at`、`given_up`、`reason` 六列，状态为 `pending`、`sending`、`sent`、`retrying`、`given_up`、`skipped`。

- 取行用条件更新占位（置为 `sending` 并给出 60 秒租期）：同一行同一时刻只有一个发送方。
- 登记方在登记后立即对这一行做一次首发，不论是不是 `serve`；其后的重试、同步与对账只在 `serve` 的发件箱线程里做，每 30 秒一轮。
- 退避与放弃窗口照搬参照实现：相对首次尝试时间，9 次尝试，57 分钟放弃；成功后计数清零。
- 首次送达的幂等键由运行编号与通道名派生，落在飞书 1 小时幂等期内。
- 尚未送达的提问卡已离开待决状态时记为 `skipped`。配置错误（通道启用但未配置接收人）同样记为 `skipped` 并写明原因，不计入重试。
- 退回文本后的交互投递记为已降级（终态）。发送结果未知累计达到 9 次后转为退回文本，而不是放弃。
- `serve` 启动时的重排只针对发送阶段放弃的行：同一提问卡已有一条可达的投递（交互或文本）时不重排另一条；同步阶段放弃的行只重试同步、不重发消息；重排时重置首次尝试时间、尝试次数与放弃标记。
- 备选：发送失败直接抛错让运行失败。通知失败不该影响沉淀运行。
- 取舍：发件箱增加了一张表的状态机；换来的是失败可见、可恢复。

### D5. 交互卡片只在链路可信时发出，否则退回文本

发送方是 `serve` 进程、交互模式已开启、自检有效、监听就绪、接收人是私聊用户且身份为机器人——五个条件全部满足才发交互卡片。

监听未就绪分两类：启动中与临时退避属暂缓，投递保持待发送、不计尝试次数，暂缓从投递首次被判为暂缓时起算并持久化，最长 120 秒，监听恢复就绪即清零；已停止、被占用、鉴权失败属不可用，立即退回文本。其余条件不满足也立即退回文本。退回文本是另一条消息、另一行投递（通道 `feishu_text`），原因写进交互那一行并追加审计事件。交互卡片连续 3 次明确失败后退回文本。发送结果未知（超时、进程被中断）时继续按同一形态与同一幂等键重试，不计入退回文本的次数——那张卡可能已经发出去了。

- 备选一：配置开了交互就一律发交互卡片。监听器启动中、退避中、被占用，或命令行触发的运行在没有 `serve` 时，都会发出可点但无人接收的卡片；回调不补推，点了没有任何反应。
- 备选二：退回文本沿用交互那一行与同一个幂等键。内容不同的两条消息共用一个键，1 小时内要么被去重不发，要么引用指向一条带按钮的消息。
- 取舍：`serve` 不在时手机上收到的仍是文本通知，需要到电脑前处理——与现状一致。

### D6. 回写只改交互卡片，并随监听可用性收口

按消息修改只支持 interactive 消息，文本投递送达即终态。提问卡版本或监听可用性发生变化时同步：版本加可用性一起与已同步的值比较，相同则不改，所以迟到点击与锁忙提示不会产生多余的修改。锁忙提示是一次性的，下一次版本变化会覆盖它。

监听进入不可用（永久停止、被占用、通道或交互模式被关闭）时，已送达且仍待决的交互卡片一次性改成"飞书按钮暂不可用，请在电脑上处理"并去掉按钮；监听恢复可用后把按钮恢复。可用性变化时对所有这类卡片各同步一次。

- 备选：只在提问卡状态变化时回写。通道开关是设置页上现成的控件，关掉之后手机上的按钮点了没人应答，也没有任何提示。
- 取舍：可用性来回切换会多次改卡，单条消息 5 QPS 的限制下不构成问题。

### D7. 回答校验顺序固定，消息引用可补绑

顺序：事件可解析且指向已知提问卡 → 回答者是配置的审批人 → 回答发生在该卡送达的那条消息上 → 操作是该卡提供的选项之一 → 受理。每一步被拒都追加一条审计事件，不改变状态；指向未知卡片的点击只进限速日志，不进审计。

- 只接受按钮点击（`action_tag` 为 `button`，无表单值）。
- 投递记录没有消息引用时（卡片已发出但没拿到 `message_id`），首条通过审批人校验的回答所在消息绑定为本卡的送达消息。同键重发能否拿回原消息编号未实测，不能把可达性押在它上面。
- 审计载荷用白名单（原因码、卡片与运行编号、事件编号、消息编号、操作），不记回调令牌、卡片原文与原始事件行。
- 备选：不校验消息引用，只认卡片编号。转发或重发的卡片上的一点也能批准。

### D8. 发往飞书的全部文本经清洗，卡片里除代码常量以外一律纯文本

清洗与脱敏对四类消息一体适用：交互卡片、文本通知、失败告警、完成通知。剔除控制字符、格式字符（含双向控制与零宽）、代理字符与非字符，折叠空白，把尖括号与命令行特殊字符（`& | < > ^ % !`）全角化，把链接样式去活化，剥离 private 片段并按密钥样式掩码，清洗后为空用占位符。

卡片上，标题、摘要、审批理由、路径、失败原因、节点摘要、结果摘要全部进 `plain_text` 文本组件；卡片结构、分组标题、按钮、链接由代码生成。内容自包含：列出单批上限内全部写入项，每项给出类型、动作、目标路径、标题、摘要与审批理由；敏感情项再给正文摘录与内容哈希前缀，并注明摘录不等于全文。敏感情项的判定（Skill 项、标记需审批、删除或覆盖核心文件）只实现一次，选项、认领与渲染共用同一个谓词。

每个字段有上限（标题 48 字、摘要 120 字、理由 160 字、路径 120 字、摘录 240 字）。体积按 UTF-8 字节计，不超过 24KB；超出时按"摘录 → 摘要 → 理由"的顺序截短并在卡上注明，任何情况下不删去写入项。回写后的卡片不再带按钮。卡片设 `enable_forward: false` 与 `update_multi: true`。

- 备选一：用 markdown 组件并做转义。飞书 markdown 的转义规则官方没有列全，`<at id=all>` 这类标签漏一个就会误 @ 全员或发送失败。
- 备选二：敏感情项在飞书上只能取消，同意须回门户。那样飞书审批对最主要的挂起原因就失去意义。
- 取舍：在飞书上批准 Skill 写入，依据的是摘录而不是全文；README 写明这一点。

### D9. 直接调用 lark-cli 的原生可执行文件

npm 的 `.cmd` 包装会让参数经过 cmd.exe：引号会打乱它的引号配对，标题里的 `&` 就可能变成命令分隔符，`%VAR%` 会被展开，且命令行上限约 8000 字符。解析顺序只有三步，没有第四步：

1. 配置的命令本身是 `.exe`（非 Windows 上是 PATH 上解析到的文件）→ 直接用。
2. 解析到 `.cmd` 包装 → 从包装脚本读出它指向的入口，取同包目录下的原生可执行文件。
3. 原生文件不存在 → 用绝对路径的 `node` 加入口脚本，保留包装脚本的自愈逻辑。

三步都得不到就不发送，投递记为失败并写明原因。解析只按 PATH 的各项，不把当前目录算进去；从包装脚本读出的入口必须落在该脚本所在包目录内。调用层做成独立对象（`LarkCliRunner`），在进程启动时解析一次并冻结；配置的 `command_args`（字符串列表）允许在命令前加参数，供替身使用。请求体以 UTF-8 字节写入 stdin。调用时设置环境变量关闭 lark-cli 的更新提示。现有的文本通知与告警走同一个解析器，`send_feishu_card` 只保留告警与完成通知两种用途，返回值区分配置错误、失败与结果未知。

- 备选一：保留退回包装脚本的路。注入面原样留着，只是记一条警告。
- 备选二：发送与改卡统一走 `api --data -`，不可信文本不进命令行。请求体字段名本机文档没写，自检确认后可以再收拢。
- 取舍：没有原生文件也没有 node 的安装发不出通知；lark-cli 本身就是"包装脚本加原生程序"的形态。

### D10. 自检是闸门：在 `serve` 内执行，通过之前不发交互卡片

`flywheel feishu-check` 调 `serve` 的接口并轮询结果，由 `serve` 自己完成，不另起消费者。测试卡片存放在提问卡表里、运行编号用固定占位值，所有按运行编号读取提问卡的查询都限定类型为提问卡，不经发件箱：自检协调器直接经调用层发送与修改，点击由监听线程按测试卡片编号转交。每次自检用独立的卡片编号与幂等键。序列：检查 lark-cli 版本与机器人身份 → 发送带按钮的测试卡片 → 立刻对它做一次修改（先确认本机能改卡，再请人点击）→ 等待点击（默认 120 秒，长等待模式 10 分钟）→ 把结果写回测试卡片并去掉按钮。失败原因分类给出：版本或身份不符、监听未就绪、被占用、未订阅、点击者不是审批人、无人点击、本机不支持改卡。超时后测试卡片改为已失效。自检状态持久化，`serve` 启动时把遗留的未完成测试卡片补改为已失效。

自检结果带指纹（可执行文件路径、版本、文件哈希、审批人集合、接收人、发送身份），存进系统设置；指纹里任何一项变化都使其失效。审批人集合取有效审批人集合的去重排序结果，与回答校验共用同一个归一化函数。自检有效是 D5 的发送条件之一。

- 备选一：自检自己起一个有界消费者。`serve` 的监听器占着订阅时它会被拒或抢走真实点击。
- 备选二：服务启动时自动自检。每次重启都发一条消息。
- 备选三：不设闸门，回调未订阅时照样发带按钮的卡片。那正是"点了没反应、也没有任何提示"的静默失败。
- 取舍：首次启用多一步人工操作；换来的是带按钮的卡片只在链路被证明可用之后才出现。

### D11. 配置与安全默认

`delivery.feishu_cli` 新增三项：`interactive`（默认 `false`）、`approver_open_ids`（默认空）、`command_args`（默认空列表）。有效审批人集合是 `approver_open_ids` 去空白后的非空项，加上非空的 `user_id`。交互模式只在通道启用、有效审批人非空、接收人是私聊用户（配置了 `user_id`）、发送身份为机器人时生效，否则不进入并记录原因。

交互模式、审批人、通道开关运行中可改并即时生效；`command`、`command_args`、`identity` 改动后需重启——配置接口对这几项返回"需重启生效"，不应用到运行中的调用层。重试节奏是代码常量，不做成配置。监听器启动时把解析到的可执行文件路径、版本与文件哈希写入审计事件。

- 备选：所有配置改动都要求重启。通道开关今天就支持运行中修改，改回去是退步。
- 取舍：审批人名单与现有的 `user_id` 一样会出现在配置读取接口里；该接口无鉴权，本机可访问者与门户同权，不扩大信任面。

### D12. 装配、线程与时间源

新组件都在 `FlywheelRuntime` 的构造函数里构造（各入口共用），顺序为：调用层 → 发件箱 → 编排器（注入终态通知回调）→ 执行线程 → 监听器 → 自检协调器。`FlywheelRuntime` 增加进程角色参数（默认 `cli`，不起任何线程），`cli.py` 的各构造点与 `create_app` 显式传入（`serve`、`mcp_stdio`、`seed`、`run`、`export_public`）。线程只在进程角色为 `serve` 时启动，清单不依赖交互模式——发件箱线程、执行线程与 `fix-approval-claim-and-recovery` 的收尾对账循环在交互模式关闭时同样运行。启动顺序：收尾与对账 → 拉起监听 → 等到监听器给出第一个状态（最多 15 秒）→ 首次补投。

需要互斥的共享状态：监听器的状态、原因、连续计数、退避截止与当前子进程句柄（停止与重拉互斥）；自检的进行中记录；"提问卡有变化"只能作为信号发给发件箱线程，其他线程不直接调用刷新函数。配置每次从当前配置对象读取，不跨调用缓存。

发件箱、监听器、自检共用一个可注入的时间源（当前时间、睡眠、带超时的等待）；取锁、续期与占位函数接受时间参数。

- 备选：组件之间用模块级全局变量互相引用。三个入口共用同一个运行时，全局状态会让测试之间互相污染。

### D13. 验证：探针先行，三级证据

真实验证排在其余实现之前：先只实现配置、调用层、最小监听与自检，在独立数据目录的沙箱 `serve` 上跑通"发卡 → 改卡 → 点击 → 回写"，把结果写进证据，再实现其余功能。沙箱不替换常驻的 `serve`——它加载的是含其他未提交改动的工作区。探针同时回答文档里没有答案的问题：机器人身份对应哪个应用、`message_id` 在返回的什么位置、真实点击事件的形态、点击者的标识类型、同一幂等键重发的返回值。采样输出与测试夹具只保留字段形态与长度，示例值换成占位符，真实标识不落盘。

- test：调用层与监听器通过可注入的替身测试，分三层——纯函数（用自检采到的脱敏输出做夹具）、进程内替身（线程加内存流伪造子进程）、一个 Windows 进程级用例（`command` 设为 `sys._base_executable`，`command_args` 指向测试目录下的假 lark-cli 脚本，脚本按 `%dp0%` 的写法配一个包装夹具）。替身要应答的命令面与输出形态写在 `tests/conftest.py` 的模块说明里，"何时吐出一次点击"由临时目录下的状态文件传递。测试里不启动真实 lark-cli（`event consume` 会创建服务端订阅），并有一个自动生效的夹具：解析出的命令若落在真实 npm 目录即判失败。
- real（自检）：经维护者授权运行自检并确认卡面排版。
- real（闭环）：沙箱 `serve`，除飞书外其余外部动作全部硬关闭，走完挂起 → 点击同意 → 续接 → 回写，以及执行失败、取消、发出后记录前重启三个分支。`card.action.trigger` 是单消费者，沙箱期间不能有另一个本服务的监听在运行。全程不写真实 Wiki。

- 备选：先实现全部功能，最后做真实验证。约三分之一的任务建在"文档推断、未实测"的前提上。

## Risks / Trade-offs

- [飞书应用未订阅卡片回调，点击永远收不到且没有预检] → 自检是闸门；未通过前只发文本；README 写出首次启用的步骤与所需权限。
- [同一飞书应用另有多处监听，回调被抢或被拒] → 被拒时退避并显示"被占用"，卡片退回文本、已发卡片收掉按钮；README 写明同一应用只在一处监听。
- [在飞书上按摘录批准 Skill 写入] → 卡片给出动作、路径、理由、摘录与哈希；README 写明；门户始终保留全文预览。
- [批准时用的是挂那一刻的计划，等待期间别的批次可能已写过同名内容] → 本次不复核；锁是重新取得的情形在审计事件里标明。
- [锁被占用时点击不生效] → 监听线程当场在卡片上写提示与预计可重试的时间，可再点。
- [`serve` 没运行时手机上只收到文本] → 与现状一致；链接与说明写明需到电脑前处理。
- [文本兜底也失败直至放弃] → 运行不受影响，门户可见投递状态；门户始终可以批准或拒绝。
- [告警与完成通知仍是一次性发送，失败不重试] → 维持现状，本次只让它们走同一个调用层与同一套清洗。
- [首页提示只看最近一个运行，较早的待审批运行不单独提示] → 既有行为，`/runs` 页有待审批计数。
- [lark-cli 升级后命令面变化] → 自检失效并退回文本，直到重新自检通过。
- [运行中的服务在重启后加载未完成的代码] → 交互模式默认关闭；探针与闭环验证都在沙箱 `serve` 上做。
- [与多项变更同改 `core/orchestrator.py`] → 本变更在编排器里只留挂起分支的登记与终态处的一个通知调用。

## Migration Plan

1. 实施顺序：`fix-approval-claim-and-recovery` 先行；与 P02、P03 的三个变更同改 `core/orchestrator.py`，确认它们的改动已提交或已冻结后才开始。
2. 合并后、不开交互模式时生效的变化：提问卡文本通知先落库并重试；lark-cli 改为直接调用原生可执行文件；发往飞书的全部文本经清洗与脱敏。
3. 首次启用交互模式：在私有 `flywheel.yaml` 里打开 `interactive` → 重启 `serve` → 运行 `flywheel feishu-check`。自检未通过前提问卡一律是文本通知。回调订阅未完成时用长等待模式，在监听在线期间到开发者后台完成订阅并发布版本。
4. 旧行迁移：已有的飞书投递改记为文本投递（通道 `feishu_text`）且视为已同步；旧的失败行，提问卡仍待决的重置为待发送，否则记为已跳过。
5. 回滚：关闭 `interactive`，待决的交互卡片会被自动改成"请在电脑上处理"。强制结束 `serve` 不会中断在工作线程里执行到一半的批准请求——Ctrl+C 会一直等它跑完；调用层与清洗的改动不随开关回退。
